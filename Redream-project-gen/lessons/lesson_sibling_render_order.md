# Lesson: Cocos/Redream 同级 sibling 的 z-order = nodes[] 尾部在前

**日期:** 2026-04-15
**状态:** ✅ 已落地（Cozy Shapes board 节点重排 底布→绣框→数字→形状→毛线→圆点）

## 事件

Cozy Shapes 操作区 (`board`) 最初按"代码里先用到谁"排节点：
```
毛线绘制层 → 填充形状层 → 圆点生成层 → 数字标签层
```
效果不对 — 数字标签应在毛线之下（被织进去），绣框应压在底布之上。用户列了 3 条约束：
> 操作区的数字标签层应该在毛线相关层之下；绣框图片应该在底布之上，其他层之下；毛线绘制层应该在形状层之上

## 根因

**Cocos/Redream 同级 sibling 的渲染顺序 = nodes[] 数组中靠后的在前（z-order 更高）。**

我习惯按"故事叙述顺序 / 代码引用顺序"排节点数组，忽略了它直接等于 z-order。

## 规则

### R1 — 设计 prefab 时，nodes[] 必须按视觉 底→顶 排序

```
nodes[0]  ← 底层（背景/底板）
nodes[1]  ← 中层
...
nodes[N]  ← 顶层（触摸响应/UI 前景）
```

### R2 — 推导 z-order 的标准流程

1. 列出所有需要的节点
2. 画一张 **视觉层级侧视图**（从地面往上看）：
   ```
   最底：底布
   ├─ 绣框（压底布）
   ├─ 内部层 A
   ├─ 内部层 B
   最顶：触摸/点击响应
   ```
3. 严格按此顺序填 nodes[]
4. **conn 的 fromNode 索引必须与新顺序同步** — 重排节点时所有引用该 prefab 的 conn 都要复核

### R3 — 特殊交互约束

- **触摸响应节点必须在最顶**：如 `圆点生成层` (La) 要在毛线/填充之上，否则点击被拦截
- **装饰边框压在内容之下**：如 `绣框` 在内容层之下（但在底布之上）
- **"被编织进去"视觉**：如 `数字标签` 在 `毛线/填充` 之下，形成被毛线盖住的错觉

## Why

- Cocos 和 Redream 都遵循这一渲染规则，不会因引擎差异而表现不同
- 若按语义顺序排，视觉会错乱，返工要同时改 nodes 顺序 + 所有引用的 conn fromNode 索引 —— 前期不显式推 z-order 就会付出双倍代价
- 数组索引就是渲染层级的"硬契约"，把它和语义顺序混用等于放弃这层保护

## How to apply

### 生成器自检

- 每个 prefab 的 nodes[] 写完后，用注释标一次 z-order：
  ```python
  "nodes": [
      {"label": "图片_圆盘底布", "type": "S"},      # 0  底
      {"label": "图片_绣框", "type": "S"},          # 1
      {"label": "数字标签层", "type": "Ly"},        # 2
      {"label": "填充形状绘制层", "type": "Ly"},    # 3
      {"label": "毛线绘制层", "type": "Ly"},        # 4
      {"label": "圆点生成层", "type": "La"},        # 5  顶（触摸响应）
  ],
  ```
- 重排节点后：`grep '"fromCard": "<prefab_id>"' gen.py` 逐条核对 fromNode

### 反模式

```
❌ board.nodes (按语义顺序)
   [0] 毛线绘制层     ← 实际应该最上
   [1] 填充形状层
   [2] 圆点生成层     ← 实际应该最顶
   [3] 数字标签层     ← 实际应该被毛线盖住
```

```
✅ board.nodes (按 底→顶 视觉层级)
   [0] 图片_圆盘底布
   [1] 图片_绣框
   [2] 数字标签层     ← 被毛线盖住
   [3] 填充形状绘制层
   [4] 毛线绘制层     ← 盖在形状/数字之上
   [5] 圆点生成层     ← 最顶，触摸响应
```
