## A类 — 分析流程规范

### A-3 帧差分分析法（判断浮层/弹窗 vs 独立界面）

**适用场景：** 录屏中出现两个视觉上相似的前后帧，需要判断"后帧"是全新界面还是弹出层。

**方法：**
1. 用 PIL 计算两帧之间的感知亮度差（`diff = L_after - L_before`）
2. 分三类：
   - **变暗区（diff < -15）**：底层内容被浮层遮罩覆盖 → 该区域是底层界面内容
   - **不变区（|diff| ≤ 15）**：两帧共同可见的元素（如顶部 HUD 未被遮罩）
   - **变亮区（diff > +15）**：前帧没有、后帧出现的内容 → 浮层/气泡本体

3. 判断依据：
   - 若变暗区覆盖 **>40%** 的屏幕像素 → 后帧存在遮罩 → **是浮层或弹窗**，不是独立界面
   - 若全屏几乎无变化 → 是状态更新（如动画），同一界面
   - 若全屏像素变化混乱 → 是完全不同的新界面

4. 用变亮区的 **BBox** 确定浮层/气泡的精确位置（x/y/w/h）

**Python 片段（PIL 实现）：**
```python
from PIL import Image
import numpy as np

def lum(arr):
    return 0.299*arr[:,:,0] + 0.587*arr[:,:,1] + 0.114*arr[:,:,2]

arr1 = np.array(Image.open('frame_before.png')).astype(float)
arr2 = np.array(Image.open('frame_after.png')).astype(float)
diff = lum(arr2) - lum(arr1)

dark_pct = (diff < -15).mean() * 100   # 遮罩覆盖百分比
new_bbox_rows = np.where((diff > 15).any(axis=1))[0]  # 新内容 y 范围
new_bbox_cols = np.where((diff > 15).any(axis=0))[0]  # 新内容 x 范围
```

**实际案例（CubeBlast 奖励关卡，2026-03-20）：**
- 误判为「界面_奖励关卡」（独立全屏界面）
- 帧差分显示：59.8% 像素变暗（全屏遮罩），新内容 BBox=x70,y568,w938,h1283
- 正确结构：`浮层_奖励列表`（OVERLAY），内含可滚动 `列表_奖励`

### A-0 节点字段格式规范 ⚠️ [JSON-ONLY·已废弃]

> **本规则仅适用于 JSON+插件流程，直接绘制模式下不适用。** 直接使用 Figma Plugin API 的 `fills`、`resize()` 等方法，无需关注 JSON 字段格式。

| 字段 | 正确格式 | 错误格式 | 后果 |
|---|---|---|---|
| 宽度 | `"w": 100` | `"width": 100` | 插件读 `layer.w` 为 undefined → 节点尺寸全0 |
| 高度 | `"h": 200` | `"height": 200` | 同上 |
| 填充色 | `"fill": "#1a5c2a"`（hex字符串） | `"fill": [{"type":"SOLID","color":{...}}]` | `parseFill()` 对 array 调 `.replace()` → **TypeError: not a function** |
| 无填充 | `"fill": "transparent"` 或 省略 | `"fill": []` | `parseFill([])`不崩溃但颜色错 |

**反面教训（2026-03-20）：** Elsa 在 CubeBlast JSON 中将 fill 输出为 Figma 原生格式数组、将尺寸字段名用了 `width`/`height`，导致用户导入插件直接报 `TypeError: not a function`。

**规则：** 生成 JSON 时，`fill` 字段**只允许是 hex 字符串**（如 `"#1a5c2a"`）或 `"transparent"`，绝不能是 list 或 dict。尺寸字段**只能是 `w` 和 `h`**。

### A-0b 内部节点子节点 key 名规范 ⚠️ [JSON-ONLY·已废弃]

> **本规则仅适用于 JSON+插件流程，直接绘制模式下不适用。**

| 位置 | 正确 key | 错误 key | 后果 |
|---|---|---|---|
| `screens[N].layers` | `layers` | `children` | 插件读 `screen.layers`，正确 |
| FRAME 内部子节点 | `children` | `layers` | 插件读 `layer.children`，用 `layers` → **所有 FRAME 内容为空** |

**规则：** 顶层 screen 的子列表用 `layers`；所有 FRAME/COMPONENT_SET/variants 内部子节点**必须用 `children`**。

### A-0c Fill 颜色值规范 ⚠️ [JSON-ONLY·已废弃]

> **本规则仅适用于 JSON+插件流程。** 直接绘制时，颜色通过 `solidFill('#888888')` 手动指定，参照 SKILL.md 2.7 灰度色板。

插件的设计哲学是**灰度低保真**，通过 `grayForNode()` 按节点深度和语义自动分配灰阶。

**规则：**
- RECTANGLE 节点的 `fill` → 填 `"transparent"` 或**不填**，让插件自动用灰度
- FRAME 节点的 `fill` → **必须**为 `[]`（不填颜色），已由插件强制 `fills=[]`
- TEXT 节点的 `fill` → 填语义颜色（如 `"#1a1a1a"` 深色文字），但非必须
- **绝对禁止**在 RECTANGLE 节点上填入游戏原始颜色（如 `"#1a5c2a"` 深绿），否则插件直接渲染真实色，破坏低保真视觉一致性

**例外：** `全屏遮罩` RECTANGLE 可保留 `fill: "#000000"`（配合 `opacity: 0.7`）。

### A-1 录屏全帧扫描（开始任何分析前必做）

1. 提取所有帧：`ffmpeg -i input.mov -vf "fps=2" /tmp/frames/frame_%03d.png`（2fps，与 SKILL.md Step 0 一致）
2. 逐帧查看**全部**帧，记录界面状态变化
3. 输出屏幕清单："共 N 帧，M 个独立屏幕：[列表]"
4. 确认清单后才开始写 JSON

**反面教训：** 只看前几帧就输出 → 漏掉后段才出现的弹窗（Enable Notifications、Search Team）

## B类 — FRAME 节点属性规范

| 属性 | 规则 | 反面教训 |
|---|---|---|
| `fill` | **禁止**在 FRAME 上设置 | 插件对 FRAME 强制应用深度灰度，JSON 的 fill 字段被忽略 |
| `clip_content` | 只有屏幕根 Frame 为 true，其余默认 false | 弹窗关闭按钮、阴影溢出部分被裁剪 |
| `stroke` | **禁止** | 可交互性由灰度差异体现，描边造成视觉噪音 |
| `corner_radius` | 圆形=w/2，药丸=h/2，**禁止魔法数字** | 尺寸变化后形状错误 |

## C类 — 控件内部结构规范

### C-1 按钮必须有"内容 Frame"

```
按钮_xxx (FRAME, interactive)
  ├── 底板_xxx_阴影  (RECT, fill=btn_shadow)   ← 视觉层：阴影
  ├── 底板_xxx       (RECT, fill=btn_main)      ← 视觉层：主板
  └── 内容_xxx       (FRAME, constraints: CENTER+CENTER)  ← 布局层
        ├── 图标_xxx (RECT, fill=icon)
        └── 文字_xxx (TEXT)
```

内容Frame尺寸计算：
- `cont_w = icon_w(60) + gap(20) + 估算文字宽（字符数 × fs × 0.6）`
- `cont_x = (按钮w - cont_w) / 2`
- `cont_y = (按钮h - cont_h) / 2`

**反面教训：** 图标+文字散落在按钮内直接用绝对坐标 → 无法整体居中，还原度差

### C-2 同功能子元素必须分组进 Frame

判断依据：**视觉上作为整体、语义上功能相同** 的多个元素必须共用一个父 Frame。

典型案例：
- 金币图标 + "+100" 文字 → `道具_金币 (FRAME)`
- 图标 + 说明文字 → `内容_xxx (FRAME)`

```
内容_关注FB (FRAME, 居中)
  ├── 图标_FB     (RECT)
  ├── 文字_Follow (TEXT)
  └── 道具_金币FB (FRAME)   ← 金币和数值作为一个道具整体
        ├── 图标_金币FB (RECT)
        └── 文字_奖励FB (TEXT)
```

**反面教训：** 子元素散落 → 无法对齐，结构不可读

### C-3 角标/徽章定位规则

角标（红点、!号等）必须定位于**父按钮右上角**：

```python
badge_x = 父按钮宽 - badge_w + 溢出量(4~10px)  # 向右溢出
badge_y = -15 ~ -20                              # 向上溢出
```

**反面教训：** 随意写 x=220（按钮中部）→ 角标出现在错误位置

### C-4 覆盖型元素（划线/遮层）必须居中于父级 Frame

**适用场景：** Toggle OFF 状态的划线、打叉图标等覆盖在父图标上的元素。

```python
# ✅ 正确：用父宽高计算居中位置
slash_x = (parent_w - slash_w) // 2
slash_y = (parent_h - slash_h) // 2
```

**反面教训：** 用 `x=5`（固定 offset）→ 父级尺寸变化时划线偏离中心，且没有对齐意图可读性。

规则：覆盖型元素的 x/y **必须基于父级 w/h 动态计算**，不允许出现与父级尺寸无关的硬编码坐标。

### C-5 同类视觉层必须合组成 Frame

**同类视觉层** 指在视觉上共同构成一个完整效果的多个节点。最典型案例：3D 按钮的阴影层 + 主板层。

```
# ❌ 错误：底板阴影 + 底板直接散落在按钮里
按钮_支持 (FRAME)
  ├── 底板_支持_阴影 (RECT)
  ├── 底板_支持 (RECT)
  └── 内容_支持 (FRAME)

# ✅ 正确：同类视觉层合组为 底板Frame
按钮_支持 (FRAME)
  ├── 底板Frame_支持 (FRAME)   ← 合组
  │     ├── 底板_支持_阴影 (RECT)   x=0, y=12
  │     └── 底板_支持 (RECT)        x=0, y=0
  └── 内容_支持 (FRAME, constraints: CENTER+CENTER)
```

底板Frame 尺寸：`x=0, y=0, w=按钮w, h=按钮h+12`（含阴影偏移量），无 fill。

**反面教训：** 底板阴影与主板散落 → 视觉层与布局层混排，结构无法直觉理解。

### C-6 划线参数规范（Toggle OFF 状态）

参考真实游戏 Toggle 的视觉效果：划线是一条**贯穿整个圆形的粗对角线**，且不应大幅超出圆形边界（无 clip_content 约束下）。

```python
# ✅ 正确参数（无 clip_content 约束下）：
slash_w  = circle_w                      # 等于圆直径，-45° 时贯穿圆心且不过长
slash_h  = max(14, circle_w // 10)       # 足够粗但不夸张
slash_x  = (circle_w - slash_w) // 2    # = 0（贴边居中）
slash_y  = (circle_h - slash_h) // 2    # 垂直居中于圆区域（相对 ch，不是 ch+12）
rotation = -45
```

**反面教训：**
- `slash_w = circle_w * 1.5`（240px for 160px circle）→ 在没有 clip 的情况下斜线大幅超出圆形，视觉混乱
- `slash_w = circle_w - 10` → 划线太短，不像斜线
- `slash_y` 相对于 ch+12 而非 ch → 划线不穿过圆心，偏上或偏下

### C-6b Toggle 圆形按钮不使用 底板Frame（无阴影）

- 普通矩形/胶囊按钮（`按钮_xxx`）使用 `底板Frame_` 实现3D阴影效果
- 小圆形开关图标（toggle 内的 `底板_xxx ON/OFF`）**直接用单个 RECT**，不加阴影
- 原因：`底板Frame` 带 `shadow_offset=12` 会使 COMPONENT_SET 高度变为 `ch+12`，导致图标居中计算基准出错

**✅ 正确 toggle 内部结构：**
```
COMPONENT_SET (w=cw, h=ch)     ← h=ch，不含阴影
  OFF variant:
    ├── 底板_xxx_OFF (RECT, 0, 0, cw, ch, SCALE+SCALE)   ← 直接 RECT，无底板Frame
    ├── 图标_xxx (RECT, icon_x, icon_y, icon_sz, icon_sz, CENTER+CENTER)
    └── 图标_划线_xxx (RECT, 0, slash_y, cw, slash_h, rotation=-45, CENTER+CENTER)
```

## F类 — 布局定位规范

### F-1 弹窗必须相对屏幕居中

```python
popup_x = (SW - popup_w) // 2   # 水平居中
popup_y = (SH - popup_h) // 2   # 垂直居中
constraints = {"horizontal": "CENTER", "vertical": "CENTER"}
```

**反面教训：** 用固定 `y=320`，弹窗在2400px的画布上显示偏上，不符合设计稿。
规则：弹窗坐标必须用公式计算，**禁止固定值**。

### F-2 clip_content 设置规则

> **⚠️ [JSON-ONLY·已废弃]** 原规则"所有 Frame 均不写 clip_content"仅适用于 JSON+插件流程。
> **直接绘制模式下**，必须手动设置 `clipsContent`：
> - 屏幕根 Frame：`clipsContent = true`
> - 滚动视口（`列表区域_`）：`clipsContent = true`
> - 其余 Frame：`clipsContent = false`（默认值，可不设）
>
> **仍然有效的设计原则：** 弹窗、按钮等 Frame 不设 clip，避免关闭按钮/阴影溢出被裁剪。

### C-7b Follow 按钮结构（道具与内容平级）

```
按钮_关注FB (FRAME)
  ├── 底板Frame_关注FB (FRAME, SCALE+SCALE)
  ├── 内容_关注FB (FRAME, MIN+CENTER)    ← 只含 图标+文字（与 内容_家长控制 同结构）
  │     ├── 图标_FB (RECT, MIN+CENTER)

  │     ├── 图标_金币FB (RECT, MIN+CENTER)
  │     └── 文字_奖励FB (TEXT, MIN+CENTER)  ← y=(frame_h-text_h)//2 垂直居中
  └── 标签_提示FB (FRAME, MAX+MIN)      ← 右上角角标
```

**反面教训：** 把 道具 放进 内容Frame → 内容Frame 无法像其他按钮一样简洁居中。

### C-2b 道具 Frame 内图标与文字必须垂直居中对齐

```python
# 道具_金币FB: w=130, h=64
图标_金币FB: y = (frame_h - icon_h) // 2  # = (64-52)//2 = 6
文字_奖励FB: y = (frame_h - text_h) // 2  # = (64-36)//2 = 14
# 两者 center_y = 32，视觉上垂直居中对齐
```

**反面教训：** 文字 `y=18` vs 应为 `y=14` → 文字视觉偏下；文字宽度不足 → 换行。

### C-7 语义相关元素必须合组进 `组_xxx Frame`

判断依据：**传达同一内容、位置相邻** 的标签+控件对，必须共用一个语义组 Frame。

最典型案例：Toggle + 对应文字标签
```
# ❌ 错误：标签和开关散落在面板内
面板_开关区 → 文字_音乐 (TEXT) + 开关_音乐 (COMPONENT_SET)  ← 直接兄弟节点

# ✅ 正确：语义相关的成组
面板_开关区 → 组_音乐 (FRAME)
                ├── 文字_音乐 (TEXT, x=0, y=0)
                └── 开关_音乐 (COMPONENT_SET, x=0, y=50)
```

- `组_` Frame 尺寸：覆盖内部所有子元素的 bounding box
- `组_` Frame 无 fill，无 clip，无 stroke
- 子元素坐标均为相对 `组_` Frame 的局部坐标

**同理适用：**
- 通知标签 + 通知开关 → `组_通知`
- 社交按钮 + 聊天开关 → 已在同一面板内，可进一步分为 `组_搜索队伍` / `组_聊天`

## I类 — 弹窗/浮层背景规范

### I-1 弹窗/浮层背景：只用 `遮罩_弹窗`，不重复铺屏幕背景

**规则：** 弹窗（`弹窗_`）和浮层（`浮层_`）的 layers 第一层只需 `遮罩_弹窗` RECT（旧名 `全屏遮罩`，已废弃），**不需要**再加一个屏幕背景 RECT。

**命名变更（2026-03-20）：**
- 旧：`全屏遮罩` ← 已废弃
- 新：`遮罩_弹窗`（弹窗半透明背景）、`遮罩_黑色`（CCLayerColor 全屏黑色）、`遮罩_锁定`（关卡锁定遮罩）

**✅ 正确结构：**
```
弹窗_开启通知 (screen)
  ├── 遮罩_弹窗 (RECT, 1080×2400, fill=#000000, opacity=0.7, SCALE+SCALE, static)
  └── 弹窗_开启通知 (FRAME, popup body, CENTER+CENTER, static)
```

**❌ 错误结构：**
```
弹窗_开启通知 (screen)
  ├── 背景图_设置暗化 (RECT)   ← 多余！叠在遮罩下面毫无意义
  ├── 遮罩_弹窗 (RECT)
  └── 弹窗_开启通知 (FRAME)
```

## H类 — 复合控件规范（高频遗漏，重点规则）

> **口诀：视觉上是一个控件 → 结构上是一个 Frame**

### H-1 复合控件必须整组进专属 Frame（禁止子元素散落）

凡是视觉上呈现为"一个控件"的多层结构，无论是否可交互，必须共用一个父 Frame。

**✅ 正确结构示例（搜索输入框）：**
```
面板_搜索输入 (FRAME)
  ├── 输入框_搜索 (FRAME, w=680, h=120)     ← 非交互部分整组
  │     ├── 底板_输入框 (RECT, SCALE+SCALE)
  │     ├── 文字_输入提示 (TEXT, MIN+CENTER)
  │     └── 图标_清除 (RECT, MAX+CENTER)
  └── 按钮_搜索 (FRAME, interactive)         ← 交互按钮独立（因为可点击）
```

**❌ 错误结构（散落）：**
```
面板_搜索输入 (FRAME)
  ├── 底板_输入框 (RECT)       ← 三者散落，无父 Frame
  ├── 文字_输入提示 (TEXT)
  ├── 图标_清除 (RECT)
  └── 按钮_搜索 (FRAME)
```

**反面教训：** 多次出现"底板+占位文字+清除图标"直接散落在面板内 → 无法整体移动/对齐，Figma 中显示为平级的无关节点，与控件逻辑严重不符。

### H-2 常见复合控件类型与命名

| 控件类型 | 前缀 | 必须包含 | 说明 |
|---|---|---|---|
| 输入框 | `输入框_` | 底板RECT + 文字_占位符 | 清除图标可选 |
| 搜索框 | `搜索框_` | 输入框_xxx（嵌套）+ 按钮_搜索（平级）| 按钮可交互，独立 |
| 下拉框 | `下拉框_` | 底板RECT + 文字_选中值 + 图标_箭头 | |
| 复选框 | `复选框_` | 底板RECT + 图标_勾选 | |
| 单选框 | `单选框_` | 底板RECT + 图标_选中 | |
| 分页器 | `分页器_` | 多个 点/按钮 子节点 | |

### H-3 判断是否需要合组的三个条件（满足一个即合组）

1. **视觉上是一个控件**：多个元素共同组成一个功能单元（如输入框的背景+文字+图标）
2. **位置联动**：移动其中一个，其他的应该一起移动
3. **语义关联**：描述同一个 UI 概念（"输入框" vs 散落的"背景矩形"+"文字"+"图标"）

## G类 — 约束（Constraints）规范

### G-1 全屏背景 / 遮罩 RECT 必须 SCALE+SCALE

适用元素：`背景图_xxx`、`遮罩_弹窗`、`遮罩_黑色`、任何覆盖整个屏幕的 RECTANGLE。

```python
constraints = {"horizontal": "SCALE", "vertical": "SCALE"}
```

原因：这些元素必须随屏幕尺寸等比缩放，使用 MIN+MIN（默认值）会在不同分辨率下出现未覆盖的区域。

**反面教训：** 不写约束 → 背景只覆盖原始尺寸，换分辨率时露底色。

### G-2 弹窗 Frame（弹窗_xxx）必须 CENTER+CENTER

```python
constraints = {"horizontal": "CENTER", "vertical": "CENTER"}
```

原因：弹窗在画布上居中显示，当屏幕 Frame 尺寸调整时，弹窗应保持居中而非固定偏移。

### G-0 NONE 父容器下的节点必须明确设置 constraints

> **适用范围：** 仅适用于 `layoutMode: NONE` 父容器的子节点。Auto Layout（HORIZONTAL/VERTICAL）容器的子节点**不写 constraints**，其定位由 AL 管理（参见 SKILL.md 2.4）。
> **API 枚举值：** `MIN`（贴顶/贴左）、`MAX`（贴底/贴右）、`CENTER`、`SCALE`。不接受 `TOP`/`BOTTOM`/`LEFT`/`RIGHT`。

- Figma 默认值 = MIN+MIN，但视觉设计中大量元素需要 CENTER/SCALE/MAX 约束
- **NONE 父容器下的每个 RECTANGLE、TEXT、FRAME、COMPONENT_SET 节点都必须设置 `constraints`**
- 不写 = 依赖默认 = 约束错误 = Figma 调整屏幕尺寸时元素错位

**COMPONENT_SET 约束选取原则（与 FRAME 相同）：**
- 在 `组_` Frame 内居中的开关 → `CENTER+MIN`（居中+贴顶）
- 贴右侧的开关（如通知开关、聊天开关） → `MAX+CENTER`（贴右+居中）
- 贴左侧的开关 → `MIN+CENTER`（贴左+居中）

**反面教训：** COMPONENT_SET 被视为"特殊节点"而遗漏 constraints → Figma 中开关在调整分辨率后位置漂移，与标签错位。

## J类 — 布局对齐与集体居中规范

### J-1 多个同类子元素必须先合组再整体居中（禁止各自单独居中）

**规则：** 当多个同类元素（如4个 toggle、3个按钮）需要在父容器内居中时，不能给每个元素单独设置居中坐标，而是：

1. 把所有元素放入一个 `组_xxx容器` Frame
2. 给该容器设置 `CENTER+CENTER` 或 `CENTER+MIN`（居中+贴顶）constraints
3. 容器内的子元素使用 `MIN+MIN`（相对容器内部定位）

**✅ 正确结构：**
```
面板_开关区 (FRAME, SCALE+MIN)
  ├── 底板_开关区 (RECT, SCALE+SCALE)
  └── 组_开关容器 (FRAME, CENTER+CENTER)   ← 一个容器整体居中
        ├── 组_音乐    (x=0,   MIN+MIN)
        ├── 组_音效    (x=240, MIN+MIN)
        ├── 组_振动    (x=480, MIN+MIN)
        └── 组_提示    (x=720, MIN+MIN)
```

**❌ 错误结构（各自硬编码位置）：**
```
面板_开关区
  ├── 底板_开关区
  ├── 组_音乐    (x=30)   ← 各自散落，无法整体居中
  ├── 组_音效    (x=292)
  ├── 组_振动    (x=572)
  └── 组_提示    (x=852)
```

**容器尺寸计算：**
```python
n = 4         # 子元素数量
item_w = 160  # 每个子元素宽度
gap = 80      # 子元素间距
container_w = n * item_w + (n-1) * gap  # = 4*160 + 3*80 = 880
container_x = (parent_w - container_w) // 2  # = (1044-880)//2 = 82
```

**适用范围：** 任何"N个等宽元素需要在容器内居中"的情况（按钮组、图标行、Tab 栏等）

### J-2 CENTER+CENTER 是主动居中指令（插件端强制生效）

**规则：** `constraints CENTER+CENTER` 不仅是"resize 时保持居中"的 Figma 约束，在插件端它会被解释为**初始布局时主动居中**。

**插件行为：**
```javascript
// 在 buildNode 中，设置 x/y 之前：
if (cst.horizontal === 'CENTER' && cst.vertical === 'CENTER') {
  x = (parent.width  - w) / 2;  // 覆盖 JSON 中的 x 值
  y = (parent.height - h) / 2;  // 覆盖 JSON 中的 y 值
}
```

**适用场景：**
- 弹窗 Frame（在屏幕中居中）
- 按钮内容 Frame（在按钮中居中）
- Toggle 图标和划线（在圆形中居中）

**重要：** 对于旋转元素（如 `图标_划线_xxx`，rotation=-45°），CENTER+CENTER 确保旋转中心就是父容器中心，从而让划线视觉上穿过圆心。

| 元素类型 | horizontal | vertical | 说明 |
|---|---|---|---|
| 全屏背景/遮罩 | SCALE | SCALE | 随屏幕拉伸填满 |
| 弹窗 Frame | CENTER | CENTER | 屏幕调整时保持居中 |
| 标题栏/顶部面板 | SCALE | MIN | 横向拉伸，贴顶部 |
| 居中按钮 | CENTER | MIN | 水平居中，Y固定 |
| 右上角关闭按钮 | MAX | MIN | 贴右上角 |
| 左侧功能按钮 | MIN | MIN | 贴左侧 |
| 右侧功能按钮 | MAX | MIN | 贴右侧 |
| 语义组 Frame | 跟随其在面板内的对齐方式 | MIN | 通常 |
| 内容居中 Frame（按钮内） | CENTER | CENTER | 内容整体居中 |

> **API 枚举对照：** `MIN`=贴顶/贴左，`MAX`=贴底/贴右，`CENTER`=居中，`SCALE`=拉伸

## K类 — 滚动列表规范

### K-1 可滚动列表三层结构（必须严格遵守）

**适用场景：** 任何视频帧中可见内容超出容器、存在手指滑动手势、或逻辑上内容项数量不定的列表。

#### 三层结构定义

```
列表区域_xxx          ← 外层 FRAME（定义可见视口区域）
  └── 列表容器_xxx    ← 内层 FRAME（承载全部列表项，高度 = 所有列表项之和）
        ├── 列表项_xxx_1
        ├── 列表项_xxx_2
        └── 列表项_xxx_N
```

| 节点 | 前缀 | 核心属性 | 说明 |
|---|---|---|---|
| 外层视口 | `列表区域_` | `clip_content: true` + `overflow: "VERTICAL"` | 决定用户能看到多少内容，高度 = 可见区域高度 |
| 内层容器 | `列表容器_` | 高度 = 全部列表项之和（可超出父级） | 内容承载体，无特殊属性 |
| 单个条目 | `列表项_` | 高度固定，宽度撑满容器 | 内部用 `底板_` + `文字_` + `图标_` 等组合 |

#### JSON 写法 ⚠️ [JSON-ONLY·仅作参考]

> **直接绘制模式请参照 SKILL.md 2.9 滚动容器代码模板。**

```json
{
  "type": "FRAME",
  "name": "列表区域_奖励",
  "x": 45, "y": 38, "w": 848, "h": 1200,
  "fill": "transparent",
  "clip_content": true,
  "overflow": "VERTICAL",
  "element_class": "data_driven",
  "children": [
    {
      "type": "FRAME",
      "name": "列表容器_奖励",
      "x": 0, "y": 0, "w": 848, "h": 1450,
      "fill": "transparent",
      "element_class": "data_driven",
      "children": [
        { "name": "列表项_奖励行_1", ... },
        { "name": "列表项_奖励行_2", ... },
        { "name": "列表项_奖励行_3", ... }
      ]
    }
  ]
}
```

#### 关键规则

1. **`列表区域_` 必须设 `clip_content: true` + `overflow: "VERTICAL"`**（缺一不可，否则 Figma 中不出现滚动行为）
2. **`列表容器_` 高度必须超过 `列表区域_` 高度**，否则 Figma 不会出现滚动
3. **`列表项_` 必须放在 `列表容器_` 内**，不能直接放在 `列表区域_` 下
4. **`overflow` 合法值：** `"VERTICAL"`（垂直滚动）/ `"HORIZONTAL"`（水平滚动）/ `"HORIZONTAL_AND_VERTICAL"`（双向）
5. **`element_class`：** 列表区域和容器均用 `data_driven`（内容由数据驱动）
6. **水平滚动列表**（如道具栏、关卡选择横滑）：将 `overflow` 改为 `"HORIZONTAL"`，`列表容器_` 宽度超出 `列表区域_` 宽度

### K-2 图标符号禁止用 TEXT 节点表示

**规则：** UI 中的图标、符号（关闭 ×、信息 i、返回箭头、设置齿轮、爱心、星星等）是**图片资产**，不是文字。必须使用 **RECTANGLE + `图标_` 前缀** 作为图片占位，绝不使用 TEXT 节点。

| 错误写法 | 正确写法 |
|---|---|
| `TEXT  文字_关闭符号  content="×"` | `RECTANGLE  图标_关闭  fill=G['rect_image']` |
| `TEXT  文字_信息符号  content="i"` | `RECTANGLE  图标_信息  fill=G['rect_image']` |
| `TEXT  文字_返回箭头  content="←"` | `RECTANGLE  图标_返回  fill=G['rect_image']` |
| `TEXT  文字_设置图标  content="⚙"` | `RECTANGLE  图标_设置  fill=G['rect_image']` |

**判断依据：** 如果一个视觉元素在真实 App 里是 SVG/PNG 图标资源（而非动态文本），就用 RECTANGLE 占位。  
只有**用户可读的文字内容**（标题、数值、描述、占位提示）才用 TEXT 节点。

**命名规范：** 图标名取图标语义，不取形状：
- `图标_关闭`（不叫 `图标_叉`）
- `图标_信息`（不叫 `图标_字母i`）
- `图标_返回`  `图标_菜单`  `图标_搜索`  `图标_设置`  `图标_分享` 等

**图标 RECTANGLE 尺寸：** 与图标视觉尺寸一致，通常比底板小（有内边距），fill 使用 `#adadad`（图片占位灰）。

**反面教训（来自 CubeBlast v8，2026-03-20）：**  
`图标_关闭按钮` 内部使用了 `TEXT 文字_关闭符号 "×"` → 视觉上虽然能看到 ×，但结构语义错误，导入真实工程后 ×  仍为硬编码文字，无法替换图标资源。

#### 反面教训（来自 CubeBlast v7，2026-03-20）

- 旧写法：用单个 `列表_奖励` 直接承载列表项，没有拆分视口与容器，没有设 `clip_content`/`overflow`
- 后果：Figma 中无 Scroll Behavior，无法原型演示滚动效果
- 修正：拆为 `列表区域_奖励` + `列表容器_奖励` + 若干 `列表项_奖励行_N`

## L类 — 布局还原完整性规范

> 本类规则来自"视觉位置/行为与参考材料不一致"的反馈模式。

### L-1 屏底元素必须延伸至屏幕底边 + BOTTOM 约束

**现象：** 底部面板（托盘、导航栏、货币栏等）在 Figma 中悬浮在屏幕中间，没有吸附到底部。

**根因：** 两个条件缺一不可都要满足：
1. `y + h = SCREEN_HEIGHT`（元素物理上延伸到屏幕底边）
2. `constraints.vertical = BOTTOM`（Figma 吸底约束，缩放时保持底部距离不变）

只设约束不延伸到底：元素仍然悬浮，只是缩放行为正确。  
只延伸到底不设约束：换设备/缩放时脱底。

**规则：**
- 识别判据：视频中元素位于可视底部 AND 始终可见（不随内容滚动）
- 写法：`y = BOTTOM_Y, h = SCREEN_H - BOTTOM_Y` + `constraints: { horizontal: 'SCALE', vertical: 'MAX' }`（MAX=贴底）
- 容器内子元素（托盘、货币栏）位置相对容器顶部计算，**不再需要各自设 BOTTOM 约束**

**反面教训（CubeBlast v9，2026-03-20）：**  
`面板_底部区域` h=402，底边到 y=1929，屏幕高度 2400，底部空出 471px → 元素悬浮在屏幕中央偏下，不贴底。

### L-2 "点击任意处退出"模式 → 全屏透明按钮，无底板

**现象：** 教学说明浮层的退出操作在视频中是"全屏点击"，但 JSON 中生成了一个小尺寸的 `按钮_继续`（585×96），并且包含了 `底板_继续按钮` RECT。

**根因：** Elsa 从文字内容（"Tap to Continue"）推断出了一个常规按钮样式，忽略了视频中退出手势的实际区域（全屏）。

**判断规则：**

| 视频中的退出手势 | JSON 结构 |
|---|---|
| 点击屏幕任意处（如教程、过场动画） | `按钮_继续`：w=1080, h=2400，无底板 RECT，文字贴底 |
| 点击明确按钮（有视觉边界） | 正常尺寸 `按钮_xxx` + `底板_xxx` RECT |
| 点击遮罩区域（弹窗外）| `遮罩_浮层` 作为交互源（已有规范 I-1） |

**全屏按钮写法：**
```json
{
  "type": "FRAME", "name": "按钮_继续",
  "x": 0, "y": 0, "w": 1080, "h": 2400,
  "fill": "transparent", "element_class": "interactive",
  "constraints": {"horizontal":"SCALE","vertical":"SCALE"},
  "children": [
    { "type":"TEXT", "name":"文字_继续提示",
      "x":240, "y":2280, "w":600, "h":90,
      "content":"Tap to Continue",
      "constraints": {"horizontal":"CENTER","vertical":"MAX"} }
  ]
}
```
**注意：** 全屏按钮无底板、无圆角；`文字_继续提示` 用 `vertical:BOTTOM` 约束，紧贴屏幕底部显示。

**反面教训（CubeBlast v8，2026-03-20）：**  
生成了 585×96 的小按钮 + `底板_继续按钮` → 导入 Figma 后视觉上多出一个灰色矩形，与视频完全不符。

### L-3 元素内部布局必须还原左右顺序和对齐

**现象：** 计时器中图标_时钟 出现在文字中央而非左侧，与参考图布局相反。

**根因：** `icon_rect()` 工具函数使用了 `constraints: CENTER+CENTER`，导致插件将图标定位到父 Frame 中心，覆盖在文字上。

**规则：**

1. **左→右排列**时（如图标+文字）：图标用 `MIN+CENTER` 约束（MIN=贴左），显式设 `x` = 内边距值
2. **文字起始 x = 图标 x + 图标 w + 间距**（不能小于这个值）
3. **居中图标**（如按钮内的图标）：可以用 `CENTER+CENTER`，但必须是 FRAME 中**唯一元素**或通过 Auto Layout 管理
4. 任何 `constraints.horizontal = CENTER` 的节点，插件会用父 Frame 宽度计算 x → **不能同时在 JSON 中设一个有意义的 x 值（会被覆盖）**

**检验方法（生成后必做）：**
```
对于每个 FRAME，列出其 children 按 x 从小到大排序，
验证该顺序是否与参考图中的视觉左→右顺序一致。
```

**反面教训（CubeBlast v9，2026-03-20）：**  
`图标_时钟` 使用 CENTER 约束 → 被放置在 435px 宽的 Frame 正中央，遮住了文字，参考图中应在左侧。

## M类 — 内容完整性规范

> 规则来源：用户反馈"漏识别元素"和"面板尺寸不足"的问题。

### M-1 面板_ vs 组_ 前缀区分

**规则：** FRAME 节点前缀根据其是否有视觉设计决定：

| 场景 | 前缀 | 判断依据 |
|---|---|---|
| 有独立视觉外观（圆角卡片/弹窗/背景色） | `面板_` | 去掉 FRAME 后用户能看出"少了一个元素" |
| 纯容器，仅为组织子节点 | `组_` | 去掉 FRAME 后视觉不变 |

**常见误判列举：**
- `面板_底部区域` → `组_底部区域`（无视觉设计，只是收纳托盘+货币栏的容器）
- `面板_进度条` → `组_进度条`（外观由子节点底板提供）
- `面板_标题横幅` → 保留 `面板_`（有金色边框+棕色背景，有视觉设计）
- `面板_计时器` → 保留 `面板_`（胶囊形状，有视觉设计）

**反面教训（CubeBlast v10，2026-03-20）：** `面板_底部区域`、`面板_进度条` 均为纯容器，被误用了视觉语义的 `面板_` 前缀。

---

### M-2 进度条组件完整结构（3 图标 + 1 文字 + 1 进度文字）

**规则：** 游戏中的"进度条"区域通常由以下5个子元素组成，必须全部识别：

```
组_进度条
  ├── 文字_关卡进度    ← 进度条上方的阶段文字（如 "Stages: 1/10"）
  ├── 图标_收集物      ← 左侧：表示积攒进度需要的游戏元素（RECTANGLE）
  ├── 底板_进度条体    ← 中间：蓝色/彩色进度条底板
  ├── 文字_进度数值    ← 叠在底板上方：当前数值（如 "0/100"）
  └── 图标_奖励物      ← 右侧：表示进度满后可获得的奖励元素（RECTANGLE）
```

**常见漏识别：** 左侧收集物图标、右侧奖励物图标（因为尺寸小，与进度条体几乎连在一起）。

**识别方法：** 观察进度条两端是否有突出的小图标，如有则必须单独列出。

---

### M-3 教学/引导面板必须撑满可用高度

**规则：** 当一个 `组_` 容器承载多个顺序步骤面板时，这些面板的垂直布局必须充分利用可用高度，不能聚集在顶部留空。

**检验标准：**
- 最后一个子面板的 `y + h` ≈ 父容器 `h`（误差不超过 5%）
- 不允许底部空白区域 > 父容器 `h` 的 10%

**修正方法：**
1. 从参考材料测量每个面板的相对高度比例
2. 按比例分配父容器高度
3. 各面板 y 值连续计算（上一个 bottom = 下一个 y 或加间距）

**反面教训（CubeBlast v10，2026-03-20）：** `组_玩法说明` h=1290，子面板只占用了前 848px，底部留有 442px 空白，与参考图严重不符。

---

### M-4 引导箭头必须识别并单独列出

**规则：** 教学界面中连接操作步骤的引导箭头（橙色/黄色大箭头图案）是独立的视觉元素，必须单独列出为 `图标_引导箭头_N`（RECTANGLE 图片占位）。

**命名规范：** `图标_引导箭头_1`、`图标_引导箭头_2`... 按出现顺序编号。

**位置定位：** 箭头通常位于两个面板之间，可能与面板在 y 轴上有重叠（箭头从上面板右下角指向下面板左上角）。用 `图标_` 前缀、`RECTANGLE` 类型，fill 使用 `rect_image`（灰色占位）。

**反面教训（CubeBlast v10，2026-03-20）：** `组_玩法说明` 完全遗漏了 3 个引导箭头，与参考图视觉差异明显。

## P 类规范：量测精度标准

### P-0 量测值必须有来源标注

骨架表中每个 y / h / w / x 值必须标注来源：

| 标注 | 含义 | 信任度 |
|---|---|---|
| `P` | Python 图像处理检测值 | 最高，直接采用 |
| `A` | AI 视觉判断值 | 需交叉验证 |
| `P+A` | Python 初值 + AI 微调 | AI 调整幅度 ≤ ±2% |

**规则：** 一张骨架表中 P 和 P+A 标注的值占比必须 ≥ 60%。若 Python 检测失败率过高，说明图像质量或检测参数需要调整，不得全部退化为 A。

### P-1 相邻区域 y 连续性

```
R[i].y + R[i].h == R[i+1].y
```

骨架表中从上到下排列的相邻大区域，上一区域的 `y + h` 必须等于下一区域的 `y`，不允许有间隙或重叠。

### P-2 大区域 h 加总 = 2400

```
sum(R[i].h for all i) == 2400
```

所有顶层大区域的 `h` 加总必须精确等于 2400。若不等，说明量测有误，必须从 Python 辅助量测重新开始。

### P-3 子元素不溢出父元素

```
child.x >= 0
child.y >= 0
child.x + child.w <= parent.w
child.y + child.h <= parent.h
```

任何子节点的边界不得超出其父容器的边界。溢出说明量测或分组有误。

### P-4 对称元素对称性验证

同一容器内被判断为"对称排列"的元素组，须验证：

```
|element_A.w - element_B.w| / avg(w) < 0.05
|element_A.h - element_B.h| / avg(h) < 0.05
```

宽高差异超过 5% 则不构成对称，需重新量测。

### P-5 同类元素等尺寸

列表项、网格单元格等同类重复元素：

```
std(sizes) / mean(sizes) < 0.05
```

尺寸变异系数超过 5% 说明量测不一致，需统一为均值后取整。

### P-6 AI 调整幅度限制

当 Python 检测值可用时，AI 调整后的最终值必须满足：

```
|final_value - python_value| / python_value <= 0.02
```

超过 2% 的偏差须在骨架表备注列说明原因（如"Python 误检边界"）。无说明的超限调整视为违规。

### P-7 验证循环通过标准

Step 2.5 验证循环的量化标准：

| 指标 | 通过阈值 | 计算方式 |
|---|---|---|
| 边缘密度比 | 0.5 ~ 2.0 | 每 120px 带内的 Figma 边缘像素数 ÷ 原图边缘像素数 |
| 水平偏移 | < 30px | 每带内边缘质心 x 坐标差 |
| 总体通过率 | ≥ 90% | 通过的带数 ÷ 总带数（2400÷120 = 20 带） |

未通过时裁切问题区域重新分析，最多 3 轮修正。3 轮后仍未通过须报告给用户。
