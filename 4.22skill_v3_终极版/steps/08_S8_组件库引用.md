## 该步做的事

### 0. `component_ref` 节点的两个核心字段区分 🔴 (易混淆)

`component_ref` 节点有**两个不同的字符串字段**, 模型容易混用:

| 字段 | 含义 | 取值来源 | 例子 |
|---|---|---|---|
| `component_ref` | **组件库条目名** (引用哪个组件) | 旧组件库 JSON 的 key (固定) | `"椭圆按钮_活动"` |
| `name` | **该实例在屏幕里的语义命名** | 视频里这个实例的实际语义 (每实例不同) | `"活动_紫罐"` / `"活动_花朵"` |

#### 例子: 屏幕里 4 个椭圆按钮引用同一组件

```json
[
  { "component_ref": "椭圆按钮_活动", "name": "活动_紫罐", ... },
  { "component_ref": "椭圆按钮_活动", "name": "活动_花朵", ... },
  { "component_ref": "椭圆按钮_活动", "name": "活动_盾牌", ... },
  { "component_ref": "椭圆按钮_活动", "name": "活动_放大镜", ... }
]
```

- `component_ref` 字段 **4 个实例都一样** (引用同一个组件库条目)
- `name` 字段 **4 个实例各不同** (各自的视频语义)

⛔ **禁止**:
- ❌ 把 `name` 写成 `component_ref` 名 (`"name": "椭圆按钮_活动"`) → 4 个实例 name 全一样, 无法区分
- ❌ 把 `component_ref` 写成实例语义名 (`"component_ref": "活动_紫罐"`) → 组件库找不到这个条目

### 1. 等比缩放计算 (来自 旧 00a component_ref 规则) 🔴

#### 缩放公式 — 必须等比

`scale = 目标h / 原始h`

非正方形组件**以高度为基准**等比推算宽度:

| 步骤 | 公式 / 数据来源 |
|---|---|
| 1. 读组件库本体尺寸 | `原始w, 原始h` (从旧组件库 JSON 读) |
| 2. 量测目标视觉尺寸 | `目标h` (S2 量测 × scale_y, 已在 S6 表 H 标记) |
| 3. 计算缩放比 | `scale = 目标h / 原始h` |
| 4. 推算目标宽度 | `目标w = 原始w × scale` |
| 5. 写入 component_ref 节点 | `w = 目标w (取整), h = 目标h (取整)` |

#### 例子

组件库 `椭圆按钮_活动` 原始尺寸 **200 × 260**, 目标视觉 h = 213 px:

```
scale = 213 / 260 = 0.819
目标w = 200 × 0.819 = 163.8 → 取整 164 (或 163, 视项目取整规则)
```

S8 写入:
```json
{ "component_ref": "椭圆按钮_活动",
  "w": 164, "h": 213, ... }
```

#### 关键铁律 (来自 旧 00a)

- ✅ **必须等比缩放**, 以**高度**为基准
- ⛔ **不允许**"用原始尺寸不缩放"
- ⛔ **不允许**横向 / 纵向各自独立缩放 (非等比)
- ⛔ **不写** `layoutSizingHorizontal` / `layoutSizingVertical` (这两个字段在 component_ref 节点上不允许出现)
- ⛔ **缩放比 ≥ 2x** 时 (S6 预检 2 已检查) 必须**先停下问用户**, 不允许 S8 阶段绕过

### 2. 同 component_ref 引用尺寸一致性 🔴

同一个 component_ref 名 (例: `椭圆按钮_活动`) 的**所有引用 w/h 必须一致**:

- 如果屏幕里 8 个 `椭圆按钮_活动` 引用, 每个的 w/h 必须相同
- 跟组件库本体 w/h 也必须一致 (后续 Figma 端需 Push to main component 同步)

#### S8 检查方法

1. 按 `component_ref` 名分组所有引用
2. 对每组, 取该组 component_ref 的**目标 h** (S6 表 H 标记的 h)
3. 如果同组多个引用的 h 不一致:
   - **优先取最大值** (一般是 hero 实例), 让其它跟齐
   - 或**问用户**"这几个引用看起来差不多大, 但 h 略不同, 取哪个值?"

S10 自检会再扫一遍这条 (跨整个 scene.json)。

### 2.5. component_ref 替换手搓的陷阱 🔴 (来自 旧 05)

用户临时要求把某个 `component_ref` 改为手搓时 (例: 组件库里某组件被删 / 改不动), 必须**把组件内部结构完整展开**, **不能只把 ref 替换成一个 FRAME 就完事**。

#### 常见坑 — 展开后 `底板_` 仍是 FRAME 而不是 RECT

❌ **错误示例** (替换 `矩形按钮_纯文本` 后):
```json
{
  "type": "FRAME", "name": "按钮_Area13",
  "children": [
    { "type": "FRAME", "name": "底板_Area13",     ← ❌ 底板_ 居然是 FRAME
      "children": [
        { "type": "RECTANGLE", "name": "底板_Area13形" },   // 又嵌一层 RECT
        { "type": "TEXT", "name": "文本_Area13", ... }
      ]
    },
    { "type": "FRAME", "name": "角标_数字1_Area13" }
  ]
}
```

这违反 v20 按钮规则 (按钮内层底板 = `底板_xxx` **RECT**, 父是 `按钮_` FRAME)。插件按名字 `底板_xxx` 会尝试上灰, 但遇到 FRAME 类型就**跳过**, 导致按钮内层无颜色。

✅ **正确做法**:

```json
{
  "type": "FRAME", "name": "按钮_Area13",
  "children": [
    { "type": "RECTANGLE", "name": "底板_Area13", ... },     ← ✅ RECT 直接挂在按钮 children
    { "type": "TEXT", "name": "文本_Area13", ... },
    { "type": "FRAME", "name": "角标_数字1_Area13", ... }
  ]
}
```

#### 执行步骤 (替换时按此走)

1. 找到要被手搓替换的 ref 节点
2. 读组件库里该组件的**实际结构**
3. 把组件内部的 FRAME 外壳**扔掉** (组件本身就是个 FRAME 层)
4. **只保留内部的 RECT/TEXT/装饰**, 直接作为外层按钮 FRAME 的 children
5. 把 ref 节点的 `overrides` 内容**回填**到对应 TEXT 的 `content`
6. 保留 ref 节点的 `x / y / w / h / constraints` 到**整组元素的对齐基准**上 (不是单个元素)

#### 自检

替换后扫一遍所有 `按钮_xxx` FRAME 的 children, **凡是 `底板_xxx` 都必须是 RECTANGLE type**, 不能是 FRAME。

### 3. Push to main component 工作流 🔴 (来自 旧 00c INSTANCE 尺寸同步铁律)

#### 问题背景

设计师在 Figma 里**直接拖动 INSTANCE 边框改尺寸**时, Figma 默认**不会**把改动同步回 Component Set 本体。结果:

- `components[].w/h` = Component Set 本体尺寸 (例: 1020 × 479)
- `screens[].layers[INSTANCE].w/h` = 各自被拖过的尺寸 (例: 499 / 438 / 360)
- 引擎按数据如实生成 .red: 父 CCNode 用 INSTANCE 尺寸, 子 CCB 用 Component 尺寸
- → **父子尺寸不匹配, 渲染视觉错位**

#### 工作流铁律 (设计师每次改 INSTANCE 后必做)

1. 设计师在屏幕里**直接改 INSTANCE 尺寸** (直观)
2. 改完选中 INSTANCE
3. 右键 → **Push changes to main component** (中文 "推送变更到主组件")
   - 快捷键 `⌥⌘Y` (macOS) / `Alt+Ctrl+Y` (Windows)
4. **验证**: 所有引用同一 Component 的 INSTANCE 应**立即自动同步**到新尺寸; 只有当前选中的变了 → 说明没生效

#### S8 阶段告知用户

S8 完成 component_ref 缩放后, 在输出末尾**主动提示用户**:

> "S8 已计算 N 个 component_ref 的缩放尺寸 (列表: …)。粘到 Figma 插件后, 如果设计师在 Figma 端**调整了 INSTANCE 尺寸**, 必须 Push to main component (`⌥⌘Y` / `Alt+Ctrl+Y`), 否则父子尺寸错位。"

#### 引擎侧不做猜测修复

引擎按数据如实生成 .red, **不做"猜测设计意图"的逻辑** (改起来风险大, 容易把别的搞坏)。这个问题必须从 Figma 端工作流解决, Claude / 插件 / extractor 三层都检查并报错, **但不自动改尺寸**。

### 6. component_ref 节点的 constraints (来自 S3 #7 + S7 #9) 🔴

`component_ref` 跟其它节点一样, **是 scene.json 里的普通节点**, constraints 写法遵循同一规则:

| 父容器 layoutMode | component_ref 写 constraints? |
|---|---|
| 屏幕 `layers` 直接子节点 (顶层) | ✅ **必须写** |
| `NONE` 父容器的子节点 | ✅ **必须写** |
| `HORIZONTAL` / `VERTICAL` 父容器的子节点 | ❌ **不写** (由 AL 接管) |

constraints 取值参考 S7 #9 "constraints 取值规则"表 — component_ref 按它在父容器内的位置取 (LEFT/RIGHT/CENTER/SCALE)。

#### 例子: NONE 父容器里的 component_ref

```json
{ "type": "FRAME", "name": "组_顶部HUD", "layoutMode": "NONE",
  "children": [
    { "component_ref": "圆形按钮_设置",
      "name": "设置按钮",
      "x": 944, "y": 25, "w": 95, "h": 112,
      "constraints": { "horizontal": "RIGHT", "vertical": "TOP" } }   // ← NONE 父容器, 必须写
  ]
}
```

#### 跟 `layoutSizing` 的区别

| 字段 | 写在 component_ref 上? |
|---|---|
| `constraints` (NONE 父容器内) | ✅ **写** |
| `layoutSizingHorizontal` / `layoutSizingVertical` (AL 父容器内子节点) | ❌ **不写** (来自 #1 等比缩放铁律, component_ref 由组件库自维护尺寸) |

⛔ **禁止** 混淆: `constraints` 是描述节点跟父容器的对齐/缩放关系, `layoutSizing` 是 AL 容器里子节点的尺寸模式。component_ref 写前者, 不写后者。

### 7. 不改组件库内部 ⛔

⛔ **S8 阶段绝对不修改组件库 JSON 文件本身**。组件库结构由 Figma 维护:

- ❌ 不重写组件库条目
- ❌ 不增删 Variant
- ❌ 不改组件库内部 fill / corner_radius / 节点结构
- ❌ 不改组件库节点的 constraints

组件库的修改由**设计师在 Figma 端做**, 不是 Claude 做。如发现组件库有问题 (S6 三项预检不过), **应在 S6 阶段停下让用户改**, 不在 S8 绕过。
