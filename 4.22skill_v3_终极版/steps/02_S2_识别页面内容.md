> - S0 上下文已读

## 这一步做什么

逐帧/逐截图扫描, 回答"屏幕里**有什么**" — 列出所有视觉元素 (节点 / 文字 / 图标 / 按钮边界), 量测每个元素的 x/y/w/h, 读出文字内容。

**这一步只识别"有什么 + 在哪 + 多大"**, 不关心:
- 元素之间怎么排列 (S3 识别布局)
- 元素之间有什么交互 (S4 识别交互)
- 哪个元素属于已知 pattern (S6 识别 pattern 命中)
- 怎么生成 JSON (S7-S9)

## 🔴 底板识别 (跟铁律 17 配套, 2026-05-22)

S2 识别每个 FRAME 时, **同时标记"该区域是否有视觉底色"**, 决定 S7 是否生成 `底板_xxx` RECT layer。

### 判定规则

| 看到 | 是否需要底板 | S7 怎么写 |
|---|---|---|
| 该区域有可见底色 / 材质 / 圆角矩形边界 (e.g. 标题 banner / 卡片行 / 进度区 / 弹窗外壳 / 内绿色 panel) | ✅ 需要 1 个底板 | 1 个 `底板_xxx` RECT 作为该 FRAME 第一个子 layer |
| 该区域是嵌套的子区域, 自己也有可见底色 (e.g. 弹窗内的绿色 panel) | ✅ 嵌套独立 1 个底板 | 在嵌套 FRAME 内再加 1 个 `底板_xxx` RECT |
| 该区域是**图片 / 插画 / 场景** (e.g. 罗伯特国王开船 / 国王+狗插画) | ❌ 不是底板 | 用 `图片_xxx` RECT, 不要写 `底板_xxx` |
| 该 FRAME 是**透明结构包装** (e.g. 组_横排 / 弹性缝隙 / 纯 layout wrapper) | ❌ 不需要底板 | 不写任何 底板 layer |

### S2 报告里怎么记

S2 元素清单里, 对每个 FRAME 行多一列 "底板?":

```
| FRAME 名 | x/y/w/h | 底板? | 备注 |
|---|---|---|---|
| 组_顶部装饰 | 0,0,1080,640 | ✅ 1 个 (绿色 banner 底) | |
| 容器_国王图 | 0,160,1080,400 | ❌ 是图片 → 用 图片_海盗船 | |
| 组_choisss行 | 0,640,1080,180 | ✅ 1 个 (绿色行底) | |
```

### 🔴 不做的事 (低保真原则, 跟铁律 17 一致)

- ❌ 不要标"该区域有阴影 / 高光 / 边框 / 渐变" → 那是高保真, 本 skill 不做
- ❌ 不要规划 底板 分多层 → 1 区域 = 1 RECT, 不分
- ❌ 不要给底板加 `底板_xxx_投影` / `底板_xxx_高光` 等子层后缀

## 该步做的事

### 1. 量测优先, 不目测估算

- 用 **Python 像素分析辅助量测**, **不允许纯目测估算**
- 获取帧/截图尺寸 → 计算 `scale_x = 1080 / W`, `scale_y = 2400 / H`
- 所有 x/y/w/h = 像素量测 × scale, **取整, 不估算** (来自 S0 第 5 节项目固定参数)
- **精度容差 ±5%** (来自 旧 06 第二层): 超出 ±5% 说明量测有误, 应重测
- **同组控件尺寸一致** (来自 旧 06 第二层): 对称布局两个按钮 w 相同; 同类按钮 FRAME 尺寸统一便于 AL 对齐

### 2. 元素逐一列举, 不跳元素

- 屏幕里**每一个**可见视觉元素都要列出
- 不能"看着差不多的就合并", 也不能"看着不重要的就跳过"
- 文字 / 图标 / 按钮底板 / 装饰角标 / 徽章 / 底标 — 全部列出

### 3. 异构内容强制分别量测

- 两种行/卡的外观明显不同 (例: 列表里"消息项 h≈190" 和"请求项 h≈280" 不同) → 单独量测每种 h
- **禁止套用统一行高**

### 4. 文字内容识别

- 读出 TEXT 元素的实际**文字内容** (用于后续 S9 写 overrides 区分实例间差异)
- 数字 / 时间 / 名字 / 状态文字 都要识别
- 字号、是否粗体、对齐方式 也可一并标注

### 5. 按钮边界识别 (只识别边界, 不判定"这是按钮")

- 识别"看起来像按钮"的色块边界 (有视觉边界 / 规则形状 / 色块对比)
- **这一步只标"按钮边界候选"**, 不下"这是按钮"的结论
- 是不是按钮交给 **S4** (帧间缩放/位移推断点击) 和 **S6** (pattern 命中)

### 6. 相似元素数量双重核查 (CCB 抽取的基础)

🔴 **关键步骤** — "看起来是一组"的相似元素 (导航项 / 列表行 / 网格卡 / 重复按钮组) 是后续 **CCB (Component) 抽取的输入基础**:
- S6 识别 pattern 命中、S7 抽 Component, 都依赖 S2 给出"这组有几个"的准确数字
- **S2 数错个数 = 后续整个 Component 抽取错** (抽出 5 个 INSTANCE 而实际应该 6 个 → 少 1 个;反之多 1 个 → 多渲染一个空位)

#### 双重核查规则

对每一组相似元素, 数量必须**双重确认**:

1. **逐帧视觉数** — 在最清晰的帧上, 逐个数出有几块独立的色块 / 图标 / 行 / 卡, **标记每一个**
2. **像素扫描验证** — 像素扫描该行/列, 找出各独立元素的 x 或 y 范围, 数独立色块数量
3. **两种方式结果一致**才记入元素清单

⛔ **禁止用 "屏幕宽度 ÷ 估算项宽度" 或 "屏幕高度 ÷ 估算行高" 反推数量** — 会少算或多算

#### 常见陷阱

- **激活态 Tab** 通常更大/更亮, 容易被视觉合并为"背景 + 图标"两个元素, 实际只是一个 Tab
- **相邻紧密的图标**, 容易把两个数成一个 (例: HUD 资源栏紧贴的 金币 + 心 + 钻石)
- **异构行混排** (消息项 + 请求项混在一个列表), 容易把不同类型的行混计 — 必须按类型分别数

#### 输出格式 (相似组团)

```text
相似组团: "贴底导航"
  双重核查:
    - 视觉数: 5  (项1, 项2, 项3, 项4, 项5)
    - 像素扫描: 5 个独立色块 (x 范围: 0-216, 216-432, 432-648, 648-864, 864-1080)
    - ✓ 一致

组内每项的 x/y/w/h: (按 #1 量测规则逐项量)
  项1: x=0,   y=2181, w=216, h=219, 内容: "主页 icon + 文字"
  项2: x=216, y=2181, w=216, h=219, 内容: "活动 icon + 文字"
  ...

相似组团: "中央列表 (异构行)"
  双重核查:
    - 视觉数: 消息项 5 + 请求项 3 = 8 行
    - 像素扫描: 8 行独立 y 范围
    - ✓ 一致
  组内每行的 x/y/w/h 按行类型分别量 (异构行高强制分别量测, 见 #3)
```

## 该步绝对不做的事 (越界 = 抢跑)

| ❌ 越界行为 | 这是哪一步的事 |
|---|---|
| 判断元素之间是 HORIZ AL / VERT AL / NONE | S3 (识别布局) |
| 计算 constraints (LEFT/RIGHT/CENTER/SCALE) | S3 |
| 判断元素 A 包含元素 B (父子关系) | S3 |
| 把按钮内的装饰挂进按钮 children | S3 / S7 (生成阶段才挂) |
| 帧差分判定 (这两帧是否同屏) | S5 (提取 flow) |
| 对比相邻帧识别滚动 / 按钮缩放 | S4 (识别交互) |
| 识别 pattern (这是不是"角标_状态" pattern) | S6 |
| 写 JSON | S7-S9 |
| **给元素起最终名字** (按命名白名单 30 个前缀) | S7 (生成阶段) |

**关于命名**: S2 阶段可以给元素打**临时描述性标签** ("胶囊按钮 1", "顶部图标", "活动框"), **不要求**按命名白名单 (`按钮_` / `底板_` 等) 命名 — 那是 S7 的事。
