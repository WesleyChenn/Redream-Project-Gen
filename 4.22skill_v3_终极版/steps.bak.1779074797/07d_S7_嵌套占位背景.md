## 1. 子 CCB 单元生成 — 扁平 FRAME (S6 #4 抽取意图 = 子 CCB 单元 时) 🔴

> 🔴 **Claude 阶段一不生成 INSTANCE 节点** — S6 #4 标记的"子 CCB 单元", S7 阶段生成**扁平 FRAME** (每个实例独立完整内容), **不是** `type: INSTANCE`。
>
> **INSTANCE 节点 + components[] 数组是 S11 `extract_components.py` 自动从扁平 FRAME 抽取后的产物 (v20.6 schema)**, 不是 S7 直接写的。

### 扁平 FRAME 生成格式 (每实例独立完整)

例: 8 个列表行 (S6 标记"子 CCB 单元", Variant 状态: 常态 / 激活, 其中部分行有"角标_王冠" 部分行没有) → S7 写 **8 个独立完整 FRAME**:

```json
// row 5 (有角标_王冠)
{ "type": "FRAME", "name": "列表项_排名5",
  "x": 50, "y": 200, "w": 1000, "h": 130,
  "layoutMode": "NONE",
  "children": [
    { "type": "RECTANGLE", "name": "底板_行", ... },
    { "type": "FRAME", "name": "排名圆",
      "children": [...] },                              // 子 CCB 单元, 内部完整 children
    { "type": "RECTANGLE", "name": "图片_头像", ... },   // 占位 RECT
    { "type": "FRAME", "name": "角标_王冠",
      "visible": true,                                   // ← row 5 显示
      "children": [
        { "type": "RECTANGLE", "name": "底板_角标王冠", ... },
        { "type": "RECTANGLE", "name": "图标_王冠", ... }
      ]
    },
    { "type": "TEXT", "name": "文本_玩家名", "content": "walid", ... }  // 实例内容直接写
  ]
},

// row 6 (没角标_王冠 — 仍然写完整 FRAME, visible: false 隐藏)
{ "type": "FRAME", "name": "列表项_排名6",
  "x": 50, "y": 340, "w": 1000, "h": 130,
  "layoutMode": "NONE",
  "children": [
    { "type": "RECTANGLE", "name": "底板_行", ... },
    { "type": "FRAME", "name": "排名圆", "children": [...] },
    { "type": "RECTANGLE", "name": "图片_头像", ... },
    { "type": "FRAME", "name": "角标_王冠",
      "visible": false,                                  // ← row 6 隐藏 (用 visible: false, 不用 variant)
      "children": [                                       // ← children 必须保留, 结构跟 row 5 一致
        { "type": "RECTANGLE", "name": "底板_角标王冠", ... },
        { "type": "RECTANGLE", "name": "图标_王冠", ... }
      ]
    },
    { "type": "TEXT", "name": "文本_玩家名", "content": "mmmmm", ... }   // row 6 独立的实例内容
  ]
}
```

### 子 CCB 显隐铁律 — 同形态父级 children 结构必须一致 🔴

S6 #4 Step D 已识别"父级高度类似但部分父级缺子集 → 需要空 Variant 的 CCB"。S7 阶段表达方式:

✅ **正确**: 所有同形态父级 (8 行) 的 children 数组**结构一致**, **都包含**`角标_王冠` FRAME (含完整 children), 需要隐藏的行写 `"visible": false`

❌ **错误**: row 5 children 数组加 `角标_王冠`, row 6 直接不放 (children 数组不含此 FRAME)
- 后果: row 5 / row 6 的 structural_fingerprint 不一致 → S11 抽不出统一 `列表项_排名` Component → 整个 Component 抽取链失败

⚠️ **S7 阶段只用 `visible: false`**, **不写** `variant: "空"` 字段 — variant / overrides 字段是 S11 抽取后 v20.6 schema 阶段才有的。

### S11 自动做的事 (S7 不写)

| 字段 | S7 阶段 | S11 阶段 |
|---|---|---|
| `type: INSTANCE` | ❌ 不写 (S7 用 FRAME) | ✓ 自动生成 |
| `component_name` | ❌ 不写 | ✓ 自动生成 |
| `variant` (含"空 Variant") | ❌ 不写 (用 visible: false 替代) | ✓ 自动根据 visible / 视觉差异分 Variant |
| `overrides` | ❌ 不写 (实例内容直接写在 children 里) | ✓ 自动从实例间 TEXT.content / 图片差异提取 |
| `components[]` 数组 | ❌ 空 `[]` | ✓ 自动填充 |
| `Variant.layers[]` 内容 | ❌ 不写 | ✓ 自动从扁平 FRAME 推断 |

### 🔴 子节点 name 100% 一致铁律 (来自 旧 04 规则 11.5, S11 抽取前提)

8 个列表行实例都包含完整 children, 而且**所有实例的 children name 必须 100% 严格一致**。S11 `extract_components.py` 用 structural_fingerprint + 子节点命名判断"是不是同一个 Component", **命名漂移会让指纹不匹配, Component 抽不出来**。

✅ **正确**:

```text
列表项_排名1            列表项_排名2            列表项_排名3
├── 底板_行             ├── 底板_行             ├── 底板_行
├── 文本_排名           ├── 文本_排名           ├── 文本_排名
├── 图标_头像框         ├── 图标_头像框         ├── 图标_头像框
└── 文本_名字           └── 文本_名字           └── 文本_名字
        ↑↑↑ 三个实例内部 name 100% 一致 ↑↑↑
```

❌ **错误 (命名漂移)**:

```text
列表项_排名1            列表项_排名2
├── 底板_行             ├── 底板_排行行   ← name 漂移
├── 文本_排名           ├── 文本_排名号   ← name 漂移
└── 文本_名字           └── 文本_玩家名   ← name 漂移
```

#### 后果

- 17 个排行榜行被识别成 17 个独立 FRAME(不抽 Component)
- 或部分聚类失败, 出现 `排行榜行` + `排行榜行_2` 两个 Component
- 设计师粘到 Figma 看到"看起来一样但是分散"的多个 Component Set

#### 怎么做到

决定一种 Component 的内部结构时, **先在心里固定一套命名模板**:

```text
列表项_xxx (模板)
├── 底板_行
├── 文本_排名
├── 图标_头像框
├── 文本_名字
└── 文本_分数
```

**所有实例都严格按这套模板填**, 不要每画一个就重起名。

#### 状态多态例外

实例之间允许的差异**只能是视觉属性** (`fill` / `corner_radius` / `opacity` / `visible`), **不能是命名差异**:

```
✅ 列表项_排名6_当前用户          ❌ 列表项_当前
├── 底板_行 (fill: 绿色)          ├── 底板_当前用户行    ← name 变了
├── 文本_排名                      ├── 文本_排名
└── 图标_头像框                    └── 图标_当前头像框   ← name 变了
```

颜色 / 形状变 → ✅ S11 归到不同 Variant
**命名变 → ❌ S11 判成不同 Component**

### 🔴 wrapper 级 visible / opacity 在扁平 FRAME 上写 (S11 自动转 INSTANCE 字段)

S7 阶段每个 FRAME 实例直接写 `visible: false` / `opacity: 0.5` 等 wrapper 级字段, S11 抽取后会自动转成 INSTANCE 节点的对应字段:

```
S7 阶段 (扁平 FRAME):                  S11 抽取后 (v20.6 schema):
{ "type": "FRAME", "name": "角标_王冠",  →  { "type": "INSTANCE", "name": "角标_王冠",
  "visible": false,                          "component_name": "角标_王冠",
  "children": [...] }                        "visible": false }      // 自动复制
```

S11 `_make_instance_node` 自动复制 wrapper 的 `visible` / `opacity` 到 INSTANCE。所以 S7 阶段**直接写在扁平 FRAME 上即可**。

### 🔴 实例间差异 — 允许 vs 应做 Variant (来自 旧 00c)

| 差异类型 | S7 阶段处理 | S11 抽取后 |
|---|---|---|
| **`TEXT.content` 文本差异** (例: 8 行玩家名不同) | ✅ 直接写在每个 FRAME 内的 TEXT.content | S11 自动提取到 `INSTANCE.overrides` |
| **`component_ref.overrides` 嵌套差异** | ✅ 直接写在每个实例内的 component_ref.overrides | S11 自动提取到 INSTANCE.overrides |
| **节点 size / position 差异** | ❌ **不允许实例差异** — 应做不同 Variant | (S11 不会提取这类差异) |
| **`fill` / `corner_radius` / 视觉属性差异** | ❌ **不允许实例差异** — 应做不同 Variant | (S11 按视觉签名分 Variant) |
| **`visible` 差异** | ✅ 直接写, 但这是 **Variant 差异 (含"空 Variant")**, 不是实例差异 | S11 自动分 Variant |

⛔ 禁止: 把 size / fill 差异作为"实例 overrides" 写 — 这些差异 S11 不会提取, 后续设计师在 Figma 端切换 Variant 时看不到差异。

## 2. 最小单元 FRAME 包装铁律 🔴 (单 RECT 抽 Component 必须包装)

S11 `extract_components.py` 脚本**只抽 FRAME, 不抽 RECT / TEXT**。 这意味着: S6 标记为"最小单元抽 Component"但实际形态是单 RECT 的节点 (例: 底板_奖励卡 RECT, 跨 16 个实例), 必须**在 S7 阶段包装成 FRAME** 才能被抽 Component。

### 哪些最小单元是单 RECT 需要包装?

| 最小单元 | 原始形态 | 是否包装 |
|---|---|---|
| 卡片底板 / 奖励卡底板 | 单 RECT (圆角矩形) | ✅ 包装 (要抽 Component 时) |
| 单一装饰 icon (无可切换状态) | 单 RECT | ⚠️ 看是否需要抽 Component (单态可不抽, 直接 RECT) |
| 进度条本体 | 单 RECT (内层) | ❌ 不抽 (旧 00d 例外 2, 数据驱动) |
| 角标 / 底标 (含底板+图标) | FRAME 含多 children | ❌ 已是 FRAME, 直接抽 |

### 包装写法

将单 RECT 套进 `组_xxx` FRAME, FRAME 自身 layoutMode=NONE, w/h = RECT 的 w/h:

```json
✅ 正确 (RECT 包装在 FRAME 内, 可抽 Component):
{ "type": "FRAME", "name": "组_奖励卡底板",
  "x": 0, "y": 0, "w": 370, "h": 270,
  "layoutMode": "NONE",
  "children": [
    { "type": "RECTANGLE", "name": "底板_奖励卡",
      "x": 0, "y": 0, "w": 370, "h": 270,
      "corner_radius": 30,
      "constraints": { "horizontal": "SCALE", "vertical": "SCALE" } }
  ]
}

❌ 错误 (单 RECT 直接挂, S11 抽不出 Component):
{ "type": "RECTANGLE", "name": "底板_奖励卡",
  "x": 40, "y": 40, "w": 370, "h": 270,
  "corner_radius": 30 }
```

### 何时不包装

如果 RECT **不需要抽 Component** (单态装饰, 例如 行底板紫色), **直接挂在父 FRAME 的 children 里**, 不需要包装。S11 会跳过 RECT 不抽。

### 包装后命名约定

- 外层 FRAME 用 `组_xxx底板` (例: `组_奖励卡底板` / `组_按钮底板`)
- 内部 RECT 仍是 `底板_xxx` (例: `底板_奖励卡` / `底板_按钮`)
- 跨多实例时, 外层 FRAME name 一致, 内部 RECT name 一致 (规则 11.5)

S11 抽完后 Component 名 = 外层 FRAME 公共前缀, 通常就是"组_奖励卡底板"。

## 2.5 Variant 内部允许异构 🔴 (规则 4, 奖励物专属)

Figma `combineAsVariants` 允许同 Component 不同 Variant 内的 layers 结构**完全不同**。 这给"枚举+占位混合"模式提供基础 (见 `06_S6 #3 例外 1 Variants 数量阈值`)。

### 例: 奖励物 Component 4 Variants 内部结构异构

```text
奖励物 Component:
├── Variant "紫箱"  : [图片_奖励 RECT]                           (1 layer, 单 icon)
├── Variant "灰箱"  : [图片_奖励 RECT]                           (1 layer, 单 icon)
├── Variant "蓝箱"  : [图片_奖励 RECT]                           (1 layer, 单 icon)
└── Variant "大炮"  : [组_奖励单元 FRAME]                        (1 layer, FRAME 包装)
                       ├── 图片_奖励 RECT (icon 占位)
                       └── 文本_数量 TEXT (dynamic, 引擎 CCLabel 控制)
```

宝箱类 Variants 内只有单 icon (没有文本); "大炮" Variant (代表道具大类) 内是 FRAME 含 [icon + 文本], 因为引擎运行时大炮类需要换 icon **同时**换数量文本。

### 为什么允许异构

Figma 端: INSTANCE 引用时, Figma 自动根据当前 Variant 切换内部 layers, **不需要每个 Variant 强制同构**。 设计师选不同 Variant 会看到完全不同的内部结构。

引擎端: 每个 Variant 是独立 sequence, 内部 layers 各自渲染。 异构 OK。

### ⚠️ 仅限"枚举+占位混合 Variant" 模式 (奖励物专属)

普通 Component (角标/底板/进度条 icon 等其他多态), 仍保持 **Variant 内部同构** (用子节点 visible 切换表达差异, 见下一节方法 A)。

> 这种 Variant 异构 + 内部 FRAME 包装的复杂判断, **极度适用于奖励物**, 其他多态通常不需要。

## 3. 多 Variants 视觉差异表达 — S7 落地的 4 种方法 🔴

S6 标记某 Component 有 N 个 Variants 时 (例: 角标_状态 3 Variants 锁/对勾/空), S7 必须让**每个 Variant 对应的实例视觉签名各不相同**, 否则 S11 抽出的 Variant 数 < N, Figma `combineAsVariants` 失败。

### S11 视觉签名的判定依据

来自 `extract_components.py` `visual_signature` 函数:
- 节点 `visible` 字段
- 节点 `fill` / `corner_radius` / `opacity` 等视觉属性
- 子节点结构 + 子节点 name 一致
- 子节点位置 (x/y) + 视觉属性

**TEXT.content 不算视觉差异** (归数据驱动 → 自动 INSTANCE.overrides)。

### 4 种视觉差异表达方法 (按推荐度排序)

#### 方法 A: 子节点 visible 切换 (🌟 主推荐, 跨 N≥2 Variants)

用于"同位置不同内容"的 Variants (锁/对勾/数字角标 等)。 children 结构 100% 一致 (规则 11.5), 通过不同子节点 visible:true/false 表达不同 Variant。

**例: 角标_状态 3 Variants (锁/对勾/空)**

```json
角标_状态 FRAME (S7 阶段每个实例 children 完全一致):
├── 底板_角标 RECT (常显, visible:true)
├── 图标_锁 RECT (锁实例 visible:true / 其他 false)
├── 图标_对勾 RECT (对勾实例 visible:true / 其他 false)
                  ← children name 100% 一致
                  ← visible 不同 → S11 切出"锁" / "对勾" Variants
                  ← 整个 角标_状态 wrapper visible:false → S11 切出"空" Variant
```

S11 自动:
- 锁实例: `_filter_invisible` 过滤掉 `图标_对勾` → Variant.layers = [底板, 图标_锁]
- 对勾实例: 过滤掉 `图标_锁` → Variant.layers = [底板, 图标_对勾]
- 空实例: wrapper 自身 visible:false → INSTANCE.visible=false (Figma 端不渲染)

#### 方法 B: wrapper visible:false 表达"空 Variant" (主推荐, 跨"显示 vs 不显示")

用于"该状态不显示" 的 Variant。 wrapper FRAME 自身 visible:false, children 保留 (跟显示实例一致)。

```json
✅ 显示实例: { "type":"FRAME", "name":"角标_状态", "visible": true, "children": [...] }
✅ 隐藏实例: { "type":"FRAME", "name":"角标_状态", "visible": false, "children": [...] }
                                                            ← children 跟显示实例 100% 一致
                                                            ← wrapper visible:false 是关键
```

S11: `_make_instance_node` 把 wrapper visible 字段传到 INSTANCE 节点, Variant.layers 过滤后 = [] → "空" Variant。

#### 方法 C: 子节点 fill / corner_radius 视觉差异 (用于"同结构不同视觉")

用于"状态视觉变化但 children 结构不变" (例: 奖励卡底板 常态 vs 待激活, 底板颜色不同)。

```json
✅ 常态: { "type":"RECTANGLE", "name":"底板_奖励卡", "corner_radius": 30 }
✅ 待激活: { "type":"RECTANGLE", "name":"底板_奖励卡", "corner_radius": 31 }
                                                       ← corner_radius 微差 → S11 切 2 Variant
```

⚠️ S7a #3 fill 规则: 手搓节点 fill 一律省略。 所以 fill 差异**不通过手写 fill 表达**, 而是通过 `corner_radius` / `opacity` 微差 (S7 允许写)。

#### 方法 D: dummy Variant (单 Variant Component 凑数, 应付 combineAsVariants ≥2 要求)

用于**单实际 Variant 的 Component** (例: 节点六边形, 8 + header 1 = 9 个视觉相同实例)。 Figma `combineAsVariants` 要求 ≥2 Variants, 必须**加 dummy 第 2 Variant**。

S11 后处理时自动 dummy (见 `11_S11_抽取导出.md` Component 修复铁律), S7 阶段**不需要**主动构造。

### 用户给的 Variants 数 vs S7 落地的差异表达

S6 表 H 给出每个 Component 的 Variants 数, S7 必须用上面 4 种方法之一**让 N Variants 真实视觉签名各异**:

| Component | S6 期望 Variants | S7 落地方法 |
|---|---|---|
| 角标_状态 | 锁 / 对勾 / 空 (3) | A (锁/对勾 子节点 visible 切换) + B (空 wrapper visible:false) |
| 奖励卡底板 | 常态 / 待激活 (2) | C (corner_radius 微差) |
| 短进度条 | 已完成 / 未完成 (2) | A (进度条_短进度 子节点 visible 切换) |
| 节点六边形 | 单 Variant | D (S11 自动 dummy) |

### TEXT.content 在 Variant 内可为 dynamic 占位

某些 Variant 内含 TEXT 节点, 但 **TEXT.content 不切 Variant** (引擎用 CCLabel 在运行时控制实际内容):

**例**: 奖励物 "大炮" Variant 内的 `文本_数量` TEXT:
- Variant 定义时: content = "x1" (设计师占位)
- INSTANCE 引用时: 不需要写 `overrides`, 引擎运行时按数据填实际值
- **不为每种数量做 Variant** (x1 / x2 / x3 不切 Variant, 是同一 Variant 内 dynamic 内容)

**类比**: 旧 skill 00d 例外 2 "进度条本体运行时数值不进 Variant" — 同样原理, 数值连续 / 频繁变化的内容由引擎运行时控制, 不切 Variant。

### S7 阶段一**禁止**的差异表达

| ❌ 禁止 | 原因 |
|---|---|
| 直接写 `type: INSTANCE` / `variant: 锁/对勾/空` | 抢跑 S11 (S7 是扁平 FRAME) |
| 写 `fill: "#xxx"` 区分锁/对勾 | 违反 S7a #3 (手搓 fill 省略) |
| 不同实例 children name 不同 | 违反规则 11.5 (S11 抽不出 Component) |
| 增删 children 表达显隐 (锁实例不画 图标_对勾) | 违反规则 11.5 |

## 5. 浮层 / 界面背景铁律

### 浮层遮罩 (`浮层_` 屏幕必须)

`浮层_` 屏幕的 `layers[0]` 必须是全屏半透明黑色遮罩:

```json
{ "type": "RECTANGLE", "name": "遮罩_浮层背景",
  "x": 0, "y": 0, "w": 1080, "h": 2400,
  "constraints": { "horizontal": "SCALE", "vertical": "SCALE" } }
```

- 插件识别 `遮罩_` 前缀后自动赋予深灰底色 + opacity=0.7
- 遮罩 fill 字段一律省略

### 界面背景 (`界面_` 屏幕有全屏背景图时)

`界面_` 屏幕的 `layers[0]` 必须是全屏 `背景_xxx` RECT:

```json
{ "type": "RECTANGLE", "name": "背景_地图场景",
  "x": 0, "y": 0, "w": 1080, "h": 2400,
  "constraints": { "horizontal": "SCALE", "vertical": "SCALE" } }
```

⛔ **禁止**: 把全屏背景塞进"中间弹性区容器"内部 — 会导致背景只占中间区高度, 顶部 / 底部无背景可透; 容器内元素绝对定位会与背景混淆。
