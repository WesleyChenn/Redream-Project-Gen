# S3 · 骨架分析【强制，生成前必须完成】

> 开始前先读取 `00_core_rules.md`，基于 S1+S2 结果执行

---

## 目标

为每个屏幕输出精确的骨架表格，验证 h 加总 = 2400。

## 执行流程（四步）

### 第一步：量测元素边界

- 用 Python 像素分析辅助量测，**不能纯目测估算**
- 获取帧尺寸 → 计算 scale_x / scale_y
- 录屏帧 H 必须排除播放器 UI

**异构列表行高：强制分别量测**
- 两种行外观明显不同 → 单独量测 h
- 禁止套用统一行高

### 第二步：物理分组

- 包含判定：文字/图标边界在色块内 → 色块为按钮 FRAME(按钮_xxx) 或容器底板 RECT(底板_xxx,父非按钮)
- 对齐判定：Y中心对齐 → HORIZONTAL；X中心对齐 → VERTICAL
- 地图区：`layoutMode: NONE`，保留绝对 x/y

### 第三步：y 坐标计算（强制顺序）

```
① 贴顶区域：从 y=0 往下叠加
② 贴底区域：从 y=2400 往上叠加
③ 中间内容区：h = 贴底起始y - 贴顶结束y
```

**禁止：** 从上往下一路叠加，导致底部重叠。

### 第四步：标注组件库匹配与角标归属（强制）

对每个元素标注：component_ref（组件名+缩放尺寸）或 手搓。

**识别顺序：**

**一、看区域类型**
- 贴底全宽 + 均分3~5个图标/文字 → 导航栏（走导航组件）
- 贴底全宽 + 2个横排切换按钮 → 状态切换导航

**导航栏元素数量强制核查（识别到导航栏后必须执行）**

⛔ **禁止用「屏幕宽度 ÷ 估算item宽度」推断导航项数量。** 这会导致少算或多算 item。

必须通过以下方式逐个确认：

1. **逐帧视觉数清楚**：在最清晰的帧上，逐个数出导航栏里有几块可见的图标/文字区域，记录每一个
2. **像素扫描验证**：对导航栏行像素扫描，找出各个高亮/激活色块的 x 范围，数出独立色块数量
3. **两种方式结果一致**才写入 `导航_项N` 的 N

常见陷阱：
- 激活态 Tab（通常更大更亮）容易被视觉合并为「背景+图标」两个元素，实际只是一个 Tab
- 反之，某些 Tab 图标相邻紧密，容易两个被数成一个
- **数完后在骨架表备注：「导航共 N 项，逐个确认：项1=xxx, 项2=xxx, ...项N=xxx」**

**二、看整体形状**
- 椭圆头像区 + 底部时间条 → `椭圆按钮_活动`
- 正圆底板 + 单图标 → `圆形按钮_xxx`
- 圆角方形 + 消息气泡 → `方形按钮_消息_激活/禁用`

**三、看内部结构**
- 只有文字 → `矩形按钮_纯文本`
- ⚠️ **进度条不再用 component_ref**（`进度条_短/宽` 是 FRAME 包装,与引擎不兼容）→ 全部手搓双层 RECT,详见下方"三补：进度条建模铁律"
- 圆角矩形 + 时间（无时钟图标）→ `底标_时间`
- 圆角矩形 + 时间（有时钟图标）→ `底标_倒计时`

**S3 时主动确认进度条交互**:遇到进度条时停下问用户"这个进度条整条可点吗?",根据回答决定外层用 `组_` 还是 `按钮_`。

**三补：进度条建模铁律（v20，引擎侧 RED Tool 硬性要求）**

引擎用 `CCProgressTimer` 节点实现进度条,需要"双层 RECT + XXX 一致"的特殊结构。所有进度条建模必须遵守以下铁律：

#### 铁律 1：三层结构（包装 FRAME + 双层 RECT，命名严格配对）

进度条的双层 RECT 必须**额外包装在一个 `组_进度_XXX` FRAME 里**,这一层包装是引擎硬性要求(类似引擎截图里的"进度条组"+"底板组"结构)。

```
组_xxx (外层容器) 或 按钮_xxx (可点击时)
└── 组_进度_XXX (FRAME)              ← v20.4 新增包装层
    ├── 底板_XXX (RECTANGLE)         ← CCSprite, Z 序低
    └── 进度条_XXX (RECTANGLE)       ← CCProgressTimer 填充, Z 序高

文本 / 图标作为 外层容器 的兄弟元素(不放进 组_进度_XXX 内):
组_xxx 或 按钮_xxx
├── 组_进度_XXX (FRAME) ← 双层 RECT 包装
├── (可选) 文本_xxx (TEXT)         ← 进度数字 / 标签
└── (可选) 图标_xxx 或 component_ref ← 左右两侧装饰 icon
```

**XXX 命名规则**：
- **三层的 XXX 必须完全一致**: `组_进度_XXX` + `底板_XXX` + `进度条_XXX`
  - **"进度"二字只出现在外层包装 FRAME,内部底板和进度条 XXX 保持简洁**
  - ✅ `组_进度_经验` + `底板_经验` + `进度条_经验`
  - ✅ `组_进度_活动` + `底板_活动` + `进度条_活动`
  - ✅ `组_进度_宝箱总` + `底板_宝箱总` + `进度条_宝箱总`
  - ❌ `组_进度_经验进度` + `底板_经验进度` + `进度条_经验进度`(内部冗余加"进度")
  - ❌ `组_进度_经验` + `底板_经验进度`(三层 XXX 不一致)
- 含方向后缀时三层都要带: `组_进度_xxx_tb` + `底板_xxx_tb` + `进度条_xxx_tb`
- **XXX 同屏唯一规则**: 同一父 FRAME 内 XXX 唯一;不同父 FRAME 内 XXX 可同名(引擎按路径识别)
  - ✅ 同屏 `按钮_活动` 内有 `底板_活动`,`组_进度_活动` 内也有 `底板_活动` —— 不冲突(父 FRAME 不同)

**包装 FRAME 尺寸**: `组_进度_XXX` 的 w/h 等于 **底板** 的 w/h(包装层视觉上和底板一样大,只是分组用,不改变视觉)。

#### 铁律 2：节点类型不可妥协

- 底板和填充层都必须是顶级 **RECTANGLE**,不能用 FRAME 包装
- ❌ 组件库的 `进度条_短` / `进度条_宽` 是 FRAME 包装结构,**与引擎不兼容**
- 进度条本体一律手搓双层 RECT,不用 component_ref（即使组件库未来调整,本规则保持稳定）

#### 铁律 3：图层 Z 序

`进度条_XXX` RECT 必须在 children 数组里**排在 `底板_XXX` 之后**(Figma 渲染时 Z 序更高,视觉上覆盖在底板上面)。

```json
✅ 正确顺序:
"children": [
  { "type": "RECTANGLE", "name": "底板_经验", ... },     ← 先(底层)
  { "type": "RECTANGLE", "name": "进度条_经验", ... }   ← 后(覆盖在上)
]

❌ 错误顺序:
"children": [
  { "type": "RECTANGLE", "name": "进度条_经验", ... },
  { "type": "RECTANGLE", "name": "底板_经验", ... }     ← 底板覆盖了填充
]
```

#### 铁律 4：进度参数命名编码（v20.3 仅方向后缀）

进度条**只把方向编码进节点名,不写百分比**。百分比由引擎运行时根据玩家数据控制。

**命名格式**:
```
进度条_<语义名>[_<方向后缀>]
底板_<语义名>[_<方向后缀>]
```

**方向后缀**(99% 场景不加,默认横向左→右):
- `_rl`：horizontal_rl 水平右→左
- `_bt`：vertical_bt 垂直下→上
- `_tb`：vertical_tb 垂直上→下

**配对铁律**: 底板和进度条名字必须**完全同名（含方向后缀）**,引擎按完整名字配对。

**进度条 RECT 必须比底板小**(详见铁律 4.5 内缩规则)。

```json
✅ 推荐写法(进度条比底板小,中心对齐):
{ "type": "RECTANGLE", "name": "底板_经验",
  "x": 0, "y": 0, "w": 500, "h": 40 },
{ "type": "RECTANGLE", "name": "进度条_经验",
  "x": 10, "y": 5, "w": 480, "h": 30 }   ← 横纵各内缩 10/5,中心对齐

❌ 错误:
{ "type": "RECTANGLE", "name": "进度条_经验",
  "x": 0, "y": 0, "w": 500, "h": 40 }   ← 同尺寸同位置(看不到底板边框)
{ "type": "RECTANGLE", "name": "进度条_经验",
  "percentage": 87 }   ← 不写 percentage 字段(运行时由引擎控制)
{ "type": "RECTANGLE", "name": "进度条_经验_p87" }  ← 不写 _p<数字> 后缀
```

**核心约定**:
- 进度条 RECT 视觉**永远画 100% 满的样子**(尺寸是 100% 满时的填充区,不按当前进度画窄)
- 不再使用 percentage 字段或 _p<数字> 后缀
- 百分比完全由引擎运行时根据玩家数据决定
- 设计师改方向时**底板和进度条必须同步改名**

#### 🔴 铁律 4.5：进度条 RECT 内缩 + 底板和进度条中心对齐（强制,最高优先级）

**进度条 RECT 必须比底板 RECT 小**(进度条表达"100% 满时填充内容的视觉区域",不含底板边框):

**内缩量规则**(按底板尺寸分级):

| 底板尺寸范围 | 横向内缩(每边) | 纵向内缩(每边) |
|---|---|---|
| 大 (w≥200, h≥80) | 10px | 10px |
| 中 (100≤w<200, 50≤h<80) | 8px | 5px |
| 小 (w<100, h<50) | 5px | 3-5px |

**中心对齐铁律**:
```
进度条 中心 (x + w/2, y + h/2) == 底板 中心 (x + w/2, y + h/2)
```

**最简实现**(底板和进度条同坐标系下,进度条 = 底板 - 2×内缩,坐标偏移 1×内缩):
```json
{ "type": "RECTANGLE", "name": "底板_活动",
  "x": 0, "y": 0, "w": 1040, "h": 95 },
{ "type": "RECTANGLE", "name": "进度条_活动",
  "x": 10, "y": 10, "w": 1020, "h": 75 }   ← 横纵各内缩 10px,中心自动对齐
```

中心点验证: 底板中心 (520, 47.5) = 进度条中心 (520, 47.5) ✅

**有 Figma 设计稿时**: 按设计稿读尺寸和坐标,但**必须验证中心点重合**。

❌ 禁止: 进度条 = 底板 同尺寸同位置(看不到底板边框,失去视觉区分)
❌ 禁止: 进度条偏离底板中心(左对齐/右对齐/顶对齐)
✅ 进度条小于底板 + 中心点重合

#### 铁律 5：方向后缀（_rl / _bt / _tb）

通过节点名后缀声明填充方向：

| 后缀 | 方向 |
|---|---|
| (无) | `horizontal_lr` 水平左→右（默认）|
| `_rl` | `horizontal_rl` 水平右→左 |
| `_bt` | `vertical_bt` 垂直下→上 |
| `_tb` | `vertical_tb` 垂直上→下 |

⚠️ **环形进度条暂不支持**(引擎未实现)。设计稿如出现环形,先用默认横向 + 标 TODO。

99% 场景用默认（不加后缀）,只在设计稿明显是其他方向时加后缀。

⚠️ **底板和进度条名字必须同步带方向后缀**,如 `底板_xxx_tb` + `进度条_xxx_tb`,不允许只一层带后缀。

#### 铁律 6：可点击 vs 非点击进度条

| 场景 | 外层包装 | 示例 |
|---|---|---|
| 进度条可点击(进活动详情)| `按钮_xxx` FRAME | 主菜单大进度条 `按钮_活动进度` |
| 进度条纯展示 | `组_xxx` FRAME | 弹窗内总进度 `组_宝箱总进度` |

判断方法：参考 00 "按钮判断清单"。整条进度条紧贴+有可操作语义 → 按钮; 纯显示 → 组。

#### 铁律 7：进度条两侧图标

进度条两侧的 icon(如金币图标 / 钥匙图标)作为**外层容器**的 children,和**包装 FRAME `组_进度_XXX`** 平级:

```
按钮_活动进度 (FRAME, 外层容器)
├── 组_进度_活动 (FRAME, 进度条包装层)
│   ├── 底板_活动 (RECT)
│   └── 进度条_活动 (RECT)
├── 图标_小火车 (RECT 或 component_ref) ← 左侧 icon (外层容器的兄弟)
├── 文本_活动进度 (TEXT)                ← 中间数字
└── 角标_倍数 (component_ref)           ← 右侧装饰
```

注意: `按钮_活动进度` 这个外层容器名带"进度"是因为整个按钮的语义就是"活动进度",不是命名要求。包装 FRAME `组_进度_活动` 必须带"进度",内部 `底板_活动` / `进度条_活动` 不带"进度"(命名规范铁律)。

**两侧图标识别**：
- 能匹配组件库 icon(如 `图标_金币`、`图标_锁`)→ 用 component_ref
- 不能匹配 → 手搓 RECT
- icon 不是进度条本体,只是兄弟元素

#### 列表型纵向进度条（每行一段独立）

当进度条**穿过列表中央**（如 Easter Pass 等级路径连接所有奖励行）时，**每行单独一个纵向短进度条**，不是整列一根贯穿条。

理由：每行独立的进度条便于按行设置已达/未达状态（如等级 19/20 已达填满，21-25 未达为空），运行时由引擎根据玩家等级动态填充。

```
每行结构（在 网格行_EasterPass_第N级 内）:
├── 组_进度_EasterPassN_tb (FRAME, w=60, h=364)              ← 包装层(带"进度")
│   ├── 底板_EasterPassN_tb (RECT, x=0, y=0, w=60, h=364)    ← 内部不带"进度"
│   └── 进度条_EasterPassN_tb (RECT, x=5, y=10, w=50, h=344) ← 内缩(横 5/纵 10)
├── 按钮_奖励_L_N
├── 按钮_奖励_R_N
└── 图标_等级徽章_N（覆盖在进度条中间）
```

每行所有进度条都画"100% 满模板",运行时引擎按玩家等级决定每行实际填充比例。

**判断方法**：
1. 在等级徽章上下位置是否有竖线**连续存在**(包括徽章覆盖区背后)→ 单条贯穿
2. 徽章左右两侧是否有线 → 双路径(两个独立 RECT,各自 `进度_路径左/右`)
3. 颜色：进度条常有**已达色(绿/金)+ 未达色(蓝/灰)**两层叠加 → 用上述双层 RECT 结构

#### 自检清单（生成前必过）

```
✅/❌ 三层结构: 组_进度_XXX(FRAME) 包含 底板_XXX + 进度条_XXX
✅/❌ 三层 XXX 完全一致(含方向后缀)
✅/❌ 包装 FRAME w/h = 底板 w/h
✅/❌ 同屏内 XXX 唯一,不和按钮内层底板重名
✅/❌ 双层都是 RECTANGLE,不是 FRAME 包装
✅/❌ children 顺序: 底板_XXX 在前, 进度条_XXX 在后(Z 序高)
✅/❌ 进度条 RECT 比底板 RECT 小(内缩,大 10/中 8-5/小 5-3)
✅/❌ 进度条中心 = 底板中心(中心点重合)
✅/❌ 外层包装正确(可点击=按钮_xxx, 纯展示=组_xxx)
✅/❌ 文本/图标作为外层容器的兄弟,不放进 组_进度_XXX 内
```

**四、看叠加附件**
- 右上角小圆 + "!" 或数字 → `角标_感叹号`
- 右上角矩形 + "×2" 类倍率 → `角标_倍数`（仅用于 ×N 格式，普通数字角标手搓）
- 好友头像框 → `头像_朋友`

**五、component_ref 预检铁律（S3 开始前必须完成，不允许边凑边用）**

识别到组件库匹配后,**必须先对整个组件库做两项预检**,通过后方可继续 S3。任一项未过 → 停下等用户修,不允许绕过。

#### 预检 1：constraints 必须全是 SCALE/SCALE

| 内部子元素 constraints | 缩放行为 | 处理方式 |
|---|---|---|
| `SCALE/SCALE` | ✅ 随 frame 等比拉伸 | 正常使用 `component_ref` |
| `LEFT/TOP` | ❌ 内容锚定左上角,frame 放大但内容不跟随 | ⛔ 停下,让用户改组件库 |
| `CENTER/CENTER` | ❌ 内容居中但尺寸不变 | ⛔ 停下,让用户改组件库 |
| 混合（部分 SCALE 部分其他）| ⚠️ 内部错位 | ⛔ 停下,让用户改组件库 |

**执行步骤**：
1. 读入组件库 JSON,遍历每个组件的 children 递归到最深层
2. 统计所有子节点的 constraints 分布
3. 若有任一组件内部子节点不是 SCALE/SCALE → **立即停下**,列出问题组件,让用户在 Figma 侧改完再继续
4. ⛔ 禁止"方案 A/B/C 凑活"：不允许"用原始尺寸不缩放"、"强制缩放明知错位"、"部分手搓部分 ref"的混合方案

**停下时的标准话术**：
> 组件库 N 个组件里有 M 个内部 constraints 不是 SCALE/SCALE,这会导致 component_ref 缩放后内部错位。请先在 Figma 里批量修改完成再继续 S3。问题组件列表：xxx / xxx / xxx

#### 预检 2：组件库尺寸基准一致性

组件库的**原始尺寸**应该是**按 1080×2400 设计稿比例**的。若有明显小尺寸组件（h < 50px 的按钮等）,说明组件库设计基准不是 1080×2400,需要用户确认。

**识别方法**：
- 对每个"按钮类/底标类/角标类"组件，对比其原始 h 和目标屏幕该类元素的典型 h
- 典型值参考（1080×2400 目标屏）：
  - 圆形按钮（icon 级）：60–100 px
  - 椭圆按钮_活动：200–300 px
  - 矩形按钮_纯文本：120–200 px
  - 角标类：40–80 px
  - 底标类：40–80 px
- 若组件原始 h 远小于典型值的 1/2 → 组件库设计基准可能不对

**处理方式**：
- **差距小**（缩放比 < 2x）：正常用 component_ref,按 v20 规则等比缩放
- **差距大**（缩放比 ≥ 2x）：停下问用户。组件库是按小尺寸设计的还是 1080×2400 设计的？
  - 若用户答"按 1080×2400 设计的,尺寸就是这么小" → 告诉用户视觉上会很小
  - 若用户答"设计稿有误,尺寸应该更大" → 等用户修完组件库再继续

**禁止绕过**：不允许自己"按目标尺寸强制缩放"而不确认 —— 这会让最终视觉和设计稿不一致。

**六、角标归属（v20 按钮分组铁律，识别到角标后必须执行）**

禁止将角标直接记录为独立元素，必须先完成以下两步再记入表格：

1. **找父本**：角标视觉上贴在哪个元素上，那个元素就是父本。
2. **应用包装规则（统一做法 B）**：
   - **父本是手搓按钮**（`按钮_xxx` FRAME）→ 角标作为该按钮的 children
   - **父本是 component_ref**（按钮类 或 Tab 状态切换类）→ 在外层包一个 `按钮_xxx` FRAME，把 component_ref 和角标都作为该 FRAME 的 children
   - 无论哪种情况，**装饰附件都必须在按钮 FRAME 的 children 内**，不得与按钮兄弟平级，不得放进普通 `组_xxx` NONE 容器

3. **确认位置关系**：量测角标相对父本的位置，记入表格。判断方法：同时量测父本宽度、角标宽度，计算居中期望值与实际值比较，误差 <10px 判定为居中。

| 常见场景 | x（相对父本左上角）| y | constraints |
|---|---|---|---|
| 右上角溢出顶部 | 父本w - 角标w + 少量偏移 | -(角标h × 0.5) | RIGHT / TOP |
| 右上角压在边缘内 | 父本w - 角标w - 偏移 | 偏移 | RIGHT / TOP |
| 底部贴边居中 | (父本w - 角标w) / 2 | 父本h - 角标h/2 | CENTER / BOTTOM |
| 主体下方居中溢出 | (父本w - 角标w) / 2 | 父本h - 3（轻微压入底边） | CENTER / TOP |


### 第五步：AL 容器对齐意图确认（强制，S4 生成前必须完成）

组件匹配表输出完毕后，紧接着对所有 AL 容器输出布局意图确认表。

**先查以下默认值表得出结论，无法确定的标注「待确认」：**

| 场景 | 典型容器 | primaryAxisAlignItems | 是否可用弹性缝隙 |
|---|---|---|---|
| 屏幕顶层 HUD / 标题栏 | 组_顶部HUD、组_标题栏 | MIN | 标题需居中时可用×2 |
| 屏幕底层导航 / 操作栏 | 组_底部导航、组_底部操作栏 | SPACE_BETWEEN | 否 |
| 外侧大组内容区（非 HUD）| 组_底部按钮区、弹窗主内容 | **CENTER** | 否 |
| 响应式中间区内各行 | 滚动区内列表行、网格行 | MIN 或 SPACE_BETWEEN | 靠右单元素时可用 |
| 列表行内部 | 列表项_xxx | MIN + 内容区FILL | 靠右单元素时可用 |
| 卡片底部行（名称+按钮）| 组_底部行 | MIN | 是，名称靠左按钮靠右 |
| 网格行 | 网格行_第N行 | SPACE_BETWEEN | 否 |
| 弹窗内容 VERTICAL | 内容区_弹窗 | MIN | 否 |

**小游戏专项规则（高优先级，覆盖上表）：**
- 顶部 HUD（生命值/金币栏）以外的**所有外侧大组**，默认 `CENTER`
- 响应式中间弹性区以外的固定高度容器，优先 `CENTER`
- 底部双按钮区：两个按钮作为整体居中，用 `CENTER`，不用弹性缝隙

**弹性缝隙使用三条强制规则（在此步骤确认，S4 执行）：**

1. **只能放在两个实体元素之间**，禁止放在 children 列表首位或末位
   ```
   ❌ [按钮_皮肤, 按钮_Level3, 弹性缝隙]   ← 缝隙在末位
   ✅ [按钮_返回, 弹性缝隙, 按钮_关闭]     ← 缝隙在中间
   ```

2. **使用前必须在本表中说明意图**：写明缝隙左侧是什么元素，右侧是什么元素，实现什么视觉效果。未在本表确认，S4 不得写入弹性缝隙。

3. **以下场景禁止用弹性缝隙，改用对应方案：**

   | 场景 | ❌ 禁止 | ✅ 正确方案 |
   |---|---|---|
   | 多个元素整体居中 | 缝隙放首位或末位 | `primaryAxisAlignItems: CENTER` |
   | 均匀分布 | 缝隙放元素之间 | `primaryAxisAlignItems: SPACE_BETWEEN` |
   | 靠右单个元素 | — | 弹性缝隙放在该元素左侧（此情况允许） |
   | 标题居中+两端按钮 | — | 弹性缝隙×2，分别放标题两侧 |
